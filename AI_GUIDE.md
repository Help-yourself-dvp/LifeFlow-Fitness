# AI Guide

## Назначение

Этот документ определяет правила взаимодействия между пользователем и AI при разработке программных проектов.

Документ не относится к конкретному проекту и может использоваться повторно.

При начале нового диалога рекомендуется прикладывать этот файл вместе с технической документацией проекта.

---

# Основной принцип

Главная цель — максимально быстро получить стабильный рабочий результат.

Красота архитектуры вторична.

Работающее приложение важнее идеального кода.

---

# Формат ответов пользователю

- Владелец читает ответы с телефона: все полезные ссылки давать прямыми и
  кликабельными (полный URL в markdown-ссылке), не «прикреплённым текстом».
- Если ссылка ведёт к действию «изменить файл на GitHub», давать её сразу в
  режиме редактирования: `.../edit/<ветка>/<путь>` (а не `/blob/...`).
- **Замена workflow — ВСЕГДА две ссылки подряд, в этом порядке** (требование
  владельца, 28.08.2026). Одной ссылки недостаточно: копировать текст надо из
  raw, а вставлять — в редактор, это разные страницы.
  1. **Откуда копировать (raw):**
     `https://raw.githubusercontent.com/Help-yourself-dvp/LifeFlow-Fitness/<ветка>/tools/github-workflows/build.yml`
  2. **Куда вставлять (редактор):**
     `https://github.com/Help-yourself-dvp/LifeFlow-Fitness/edit/<ветка>/.github/workflows/build.yml`

  В имени ветки есть слеш (`arena/…`) — в raw-URL он пишется как есть, без
  экранирования. Ссылку на `/blob/…` вместо raw давать нельзя: из просмотрщика
  длинный файл копируется не целиком.
- Проверочные списки — короткими пронумерованными шагами.

# Принцип обратной связи

Комментарии и идеи пользователя — это предложения к обсуждению, а не безусловные задачи к реализации.

AI обязан:

- отвечать **по каждому пункту** пользователя подробно и развёрнуто, без пропусков, усечений и объединений: если пользователь прислал N пунктов, ответ обязан содержать ровно N подробных блоков с объяснением логики, вариантов и принятых решений;
- если AI не согласен с предложением — честно сказать об этом и предложить альтернативу с аргументами, а не молча реализовывать;
- если есть решение лучше предложенного — предложить его с техническим обоснованием;
- фиксировать этот принцип в памяти диалога и не забывать его между версиями.

Финальное слово всегда за пользователем: если после аргументов AI он подтверждает исходный вариант — реализуется он.

# Уровень пользователя

Пользователь не является профессиональным разработчиком.

Не предполагается знание:

- Android SDK
- Java
- Kotlin
- Gradle
- YAML
- Git
- GitHub Actions

Все инструкции должны быть рассчитаны на начинающего разработчика.

---

# Стиль ответов

Основной принцип:

Меньше обсуждений — больше готовых решений.

Ответ должен состоять из:

1. Краткого объяснения (если оно действительно необходимо).
2. Пошаговых действий.
3. Полностью готового кода или готового текста.

Не нужно подробно обсуждать каждое небольшое техническое решение.

AI самостоятельно принимает мелкие технические решения.

Согласование требуется только если изменение влияет на:

- функциональность приложения;
- архитектуру;
- безопасность данных;
- совместимость версий.

---

# Принятие решений

AI самостоятельно принимает мелкие технические решения.

Например:

- название функций;
- название документов;
- расположение кода;
- оформление.

Согласование требуется только для решений, влияющих на функциональность проекта или архитектуру.

---

# Работа с кодом

Если изменение небольшое, НЕ присылать полный файл.

Предпочтительно заменить:

- одну функцию;
- один HTML-блок;
- один CSS-блок;
- один раздел документа.

Полный файл присылается только если изменение действительно затрагивает большую часть файла.

---

# Изменение существующего кода

Если изменение небольшое — не присылать полный файл.

Предпочтительно заменять:

- одну функцию;
- один HTML-блок;
- один CSS-блок;
- один раздел документа.

Полный файл используется только если изменение затрагивает значительную часть проекта.

Перед предложением полной замены AI должен оценить, нельзя ли решить задачу локальным изменением.

---

# Работа с версиями

Одна версия приложения должна содержать одну небольшую законченную задачу.

Не объединять множество изменений в один релиз.

Каждая новая версия должна успешно устанавливаться поверх предыдущей.

---

# Стабильность

Стабильность всегда важнее новых функций.

Перед добавлением новой функции необходимо убедиться, что текущая версия работает корректно.

---

# Работа с GitHub

Все действия должны описываться максимально подробно.

Не использовать инструкции вида «отредактируйте файл».

Следует писать:

- какой файл открыть;
- куда нажать;
- что заменить;
- что написать в Commit;
- что проверить после сборки.

---

# Документация

Каждый проект должен иметь техническую документацию.

Основной документ проекта: PROJECT.md

Сопроводительные документы (с 0.4.15): CHANGELOG.md (краткая история версий), ROADMAP.md (этапы и монетизация), PRIVACY.md (конфиденциальность), THIRD_PARTY.md (лицензии), POSTPONED.md (отложенные и провалившиеся подходы), SESSION_HANDOFF.md (передача разработки), DATA_SOURCES.md и COMMAND_DICTIONARY.md (источники и словарь парсера).

Документация должна обновляться только после действительно значимых изменений.

Не следует тратить большое количество времени на поддержку документации.

---

# Архитектура

Не усложнять проект без необходимости.

Если простое решение решает задачу — оно предпочтительнее сложного.

---

# Зависимости

Не добавлять новые библиотеки без необходимости.

Перед использованием нового плагина необходимо оценить риск нарушения работоспособности приложения.

---

# Изменение существующего кода

Не переписывать рабочий код без причины.

Минимизировать объем изменений.

Максимально сохранять существующую архитектуру.

---

# Безопасность данных

При обновлении приложения пользовательские данные должны сохраняться.

Если существует риск их потери, AI обязан предупредить об этом заранее.

---

# Работа с APK

Приоритетом является сохранение совместимости обновлений.

Подпись APK должна оставаться постоянной.

Пользователь не должен удалять приложение перед установкой новой версии.

---

# Приоритет разработки

Приоритет задач:

1. стабильность;
2. удобство пользователя;
3. упрощение процесса разработки;
4. новые функции;
5. косметические изменения.

---

# Инфраструктура проекта

Изменения файлов инфраструктуры (GitHub Actions, Gradle, подпись APK, Capacitor) считаются высокорискованными.

Для таких файлов:

- менять минимально необходимый участок;
- не переписывать файл полностью без необходимости;
- после каждого изменения обязательно проверять успешность сборки.

---

# Порядок разработки

1. Исправление ошибок.
2. Стабильность.
3. Удобство пользователя.
4. Ускорение процесса разработки.
5. Новый функционал.
6. Косметические изменения.

Если существует несколько решений задачи, предпочтение отдается наиболее простому и надежному.

### Золотой стандарт нативного workflow (build.yml) с первого дня

Чтобы владельцу **никогда не приходилось вручную редактировать `.github/workflows/build.yml`** на протяжении жизни проекта (из-за ограничений прав GitHub App на изменение workflows), в первом же коммите нового проекта AI обязан развернуть **полный универсальный нативный каркас**:

1. **Автоматическое чтение версии**: workflow с самого начала читает версию из `version.txt` (`APP_VERSION="$(tr -d '[:space:]' < version.txt)"`). Номер сборки берется из `${{ github.run_number }}`. Для выпуска релиза достаточно изменить `version.txt` и JS-константу — workflow трогать не нужно.
2. **Постоянная подпись (Keystore)**: с первого дня настраивается восстановление стабильного `debug.keystore` (из секрета `DEBUG_KEYSTORE_BASE64` или генерации постоянного ключа), чтобы все последующие сборки устанавливались поверх без удаления приложения и потери данных.
3. **Полный набор системных разрешений в AndroidManifest.xml**:
   - Уведомления и планировщик: `POST_NOTIFICATIONS`, `SCHEDULE_EXACT_ALARM`, `USE_EXACT_ALARM`, `RECEIVE_BOOT_COMPLETED`, `WAKE_LOCK`.
   - Фоновая работа и батарея: `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`.
   - Медиа и ввод: `RECORD_AUDIO`, `CAMERA` + `<uses-feature android:name="android.hardware.camera.any" android:required="false" />` (пункт «Камера» в WebView file picker).
   - Датчики и активность: `ACTIVITY_RECOGNITION`, `Sensor.TYPE_STEP_COUNTER`, `Sensor.TYPE_STEP_DETECTOR`.
   - Здоровье и внешние устройства: `android.permission.health.READ_STEPS`, `READ_TOTAL_CALORIES_BURNED`, `READ_EXERCISE`, `READ_SLEEP`, `activity-alias` `ViewPermissionUsageActivity`.
4. **Блок видимости пакетов (`<queries>`)**: с первого дня объявлять интенты Health Connect (`android.health.connect.action.HEALTH_HOME_SETTINGS`, `androidx.health.ACTION_HEALTH_CONNECT_SETTINGS`) и пакеты сопутствующих приложений (`com.google.android.apps.healthdata`, `com.huami.watch.hmwatchmanager` для Zepp/Amazfit, Samsung Health).
5. **Универсальные нативные мосты в MainActivity.java**:
   - IME-прогрев фокуса для предотвращения залипания клавиатуры.
   - Мост `JavascriptInterface` (`FitFlowExport`): сохранение бэкапов через системный SAF `ACTION_CREATE_DOCUMENT` (без прав на всю память), голосовой ввод, чтение SharedPreferences для виджета, опрос системных датчиков.
   - Виджет рабочего стола (`AppWidgetProvider` с поддержкой компактного и расширенного размера).
   - R8 8.5.35 в buildscript для поддержки Java-21 байткода современных библиотек (LiteRT, WASM).
6. **Принцип изоляции логики в Web/JS слое**: нативный каркас служит надежной универсальной «платформой», а вся бизнес-логика, математика, алгоритмы Master Priority, SQLite WASM и интерфейс живут в `app.js` / `index.html` / `style.css`. Это позволяет AI развивать проект на 100% автономно через обычные коммиты без привлечения пользователя.

### Правило обязательной двойной проверки релиза перед выдачей ссылки

Перед тем как отправить пользователю ответ о готовности сборки и ссылку на скачивание, AI ОБЯЗАН:
1. **Проверить фактический номер сборки на GitHub**: выполнить `gh run list -L 1` и `gh release list -L 1`. Ссылка в ответе обязана вести СТРОГО на тот релиз, который скомпилирован именно из последнего коммита с кодом решения (а не из промежуточных коммитов документации).
2. **Сверить версию во всех файлах**: константа `FITFLOW_BUILD` в `app.js`, версия в `index.html`, `version.txt` и тег релиза GitHub обязаны совпадать до единого символа.
3. **Проверить работоспособность функций в коде**: убедиться, что вызываемые функции существуют (нет `ReferenceError`), селекторы присутствуют в HTML, а тесты `test-parser.js`, `test-food-db.js`, `test-ui-init.js` и `node -e "require('./app.js')"` завершились с успехом.

## Диагностика: чинить причину, а не симптом (урок 0.9.11 → 0.9.12)

Реальный случай из проекта, стоивший лишней версии и лишней сборки у владельца.

**Симптом:** шаги за пропущенные дни не подтягивались задним числом.
**Что сделали в 0.9.11:** нашли четыре настоящих дефекта (ранний снимок блокировал
дозаливку, атрибуция через полночь, сложение часов и телефона, отсутствие истории
сна) и починили их. Три из четырёх были реальными багами. Но шаги всё равно не
пришли, а вот сон — пришёл.
**Настоящая причина (0.9.12):** чтение истории шло **одной страницей**, а API
отдаёт данные порциями с `pageToken`. Записей о сне мало — он влезал в первую
порцию; записей о шагах тысячи — свежие дни не доезжали.

Выводы, применимые к любой задаче:

1. **Расхождение в поведении двух похожих веток — главная улика.** «Сон работает,
   шаги нет» при одинаковом коде дозаливки означало, что дело не в общей логике
   слияния, а в объёме данных. Именно эту разницу и надо было объяснить в первую
   очередь.
2. **Починка нескольких правдоподобных дефектов не заменяет объяснения симптома.**
   Прежде чем закрывать задачу, ответить: «какой конкретно из найденных дефектов
   даёт наблюдаемое поведение?» Если ответа нет — причина не найдена.
3. **Искать эталон в собственном коде.** Рядом уже жила функция `syncNow`, которая
   читала шаги постранично и имела на это подробный комментарий. Сверка новой
   функции с работающим аналогом закрыла бы вопрос сразу.
4. **Ограничения API читать до конца.** Постраничная выдача, лимиты и окна времени
   ломаются молча: данные не приходят, ошибки нет.

## Симметрия функций: если у соседа есть, проверь, есть ли здесь (урок 0.9.14)

**Симптом:** тренировки с часов подтягивались только за трое суток, хотя шаги и
сон дозаливались за 30 дней.

**Причина:** обратную заливку писали по одной сущности за раз — шаги в 0.8.11,
сон в 0.9.11. Для тренировок аналогичной функции не написали вообще, и
отсутствие кода никак себя не проявляло: синхронизация «работала», данные шли,
просто окно было в десять раз уже. Такую дыру не видно ни в тестах, ни в логах —
её видно только сопоставлением.

Практический приём: **перед разбором держать в голове таблицу «сущность × слой»**.
Для этого проекта — шаги / сон / тренировки / показатели тела по слоям
«чтение в Kotlin», «мост в Java», «колбэк в window», «вызов раз в сутки»,
«пересчёт сводки дня». Пустая клетка в таблице почти всегда и есть ошибка.
В 0.9.14 таких клеток нашлось три сразу: не было `readWorkoutsHistory`, не было
моста `syncHealthWorkoutsHistory`, и вдобавок обнаружилось, что колбэк
`onHealthBodyMetricsReceived` (написан в 0.8.23) вообще не присвоен в `window` —
вес с умных весов не доезжал полтора десятка версий, и никто не жаловался.

Второй вывод: **починка «доставки» данных ничего не даёт, если данные потом
теряются на следующем слое**. Тренировка, добавленная задним числом, попадала в
дневник, но в график активности — нет: сводка прошлого дня не пересчитывалась.
Прежде чем закрывать задачу, проследить путь данных до самого экрана, где
владелец ждёт результат.

Третий вывод: **дублирующиеся пути разбора надо сводить в одну функцию сразу**.
Ежедневный синк и месячная заливка разбирали бы один и тот же формат по-своему
и неизбежно разошлись бы. Общее чистое ядро (`mergeWatchWorkoutsBackfill`) заодно
стало тестируемым прогоном, а не только регуляркой по исходнику.

## Свои значения вместо фиксированного набора (урок 0.9.12)

Захардкоженный в разметке набор вариантов (пресеты таймера 30/60/90/120) выглядит
как мелочь, пока пользователю не понадобится значение за пределами набора. Правила:

- Наборы значений, которые пользователь может захотеть изменить, держать
  **в состоянии**, а не в HTML.
- Давать возможность и добавить своё, и убрать лишнее — иначе список только растёт.
- Защищать граничный случай: удалить **последний** элемент нельзя, иначе функция
  перестаёт работать вовсе.
- Не превращать это в экран настроек: одно поле ввода и долгое нажатие для
  удаления — достаточно. Принцип владельца «не городить много кнопок» действует
  и здесь.

## Скорость ввода — это тоже функция (урок 0.9.12)

Жалоба «слишком долго вводить» — полноценный дефект, а не пожелание. Пять
одинаковых подходов требовали десяти нажатий и двадцати заполненных полей.
Решение: одна строка «5x10x12».

- Принимать **все варианты написания**, которые пользователь может набрать:
  латинская `x`, кириллическая `х`, `*`, `×`, пробел. Требовать конкретный символ
  на телефонной клавиатуре — значит переложить работу на пользователя.
- Быстрый ввод не заменяет обычный, а дополняет его: результат разворачивается в
  те же поля, которые можно поправить поштучно.
- **Термины пользователя важнее терминов разработчика.** Владелец отдельно
  указал, что «повторы» и «повторения» — разные вещи. Спорить с языком предметной
  области не нужно.

## Отмена ввода обязательна там, где ввод длинный

Если заполнение формы занимает больше нескольких секунд, обязаны существовать оба
пути: сохранить и отменить. Черновик, который нельзя очистить, переносит записи в
следующую сессию. При этом отмена длинного ввода — через подтверждение, а очистку
выполнять **той же функцией**, что и после сохранения, чтобы два пути не разъехались.

## Практика Capacitor / Android (накопленный опыт)

- Локальные Android-уведомления нужно проверять не только сразу после создания, но и
  при заблокированном экране, после перезагрузки телефона и на прошивках с агрессивной
  экономией батареи. Экран с настройками уведомлений, батареи и автозапуска обязателен
  для Honor, Xiaomi, Huawei, Samsung и похожих устройств.
- Короткий `body` уведомления может обрезаться системным интерфейсом. Для длинного
  текста Android следует передавать `largeBody` и `summaryText`; нажатие на уведомление
  должно открывать в приложении полный текст в собственном диалоге.
- Android-виджет не может читать `localStorage` WebView напрямую. Для него нужен мост
  JavaScript → JavascriptInterface → SharedPreferences и обновление SharedPreferences
  после каждого сохранения данных, а не только после перезапуска приложения.
- Нативный виджет, уведомления и сборочный workflow требуют проверки на реальном APK:
  успешный JavaScript-тест не заменяет Android-проверку.
- Если GitHub App не разрешает менять `.github/workflows`, рабочий workflow можно
  подготовить идентичной копией вне `.github` и вручную заменить только этот файл в
  той же рабочей ветке. Не переносить workflow напрямую в `main` до проверки сборки.

### Безошибочная ручная замена GitHub Actions workflow

**Важно, когда она нужна (с версии 0.2.5):** сборочный workflow FitFlow читает номер
версии из файла `version.txt` в корне репозитория. Обычные релизы (HTML/CSS/JS и смена
номера версии) собираются автоматически после пуша — вручную workflow больше не заменяют.
Ручная замена `.github/workflows/build.yml` требуется ТОЛЬКО при нативных изменениях:
Gradle-зависимости, новые Capacitor-плагины, правки MainActivity/виджета, генерация иконок.
Полный актуальный процесс релиза и шаблон ответа пользователю — в SESSION_HANDOFF.md
(раздел «Актуальный процесс релиза»).

Если текущая GitHub App не имеет permission `workflows`, агент не сможет отправить
изменение `.github/workflows/*.yml`. Для безопасной ручной замены нужно:

1. Агент отправляет в рабочую ветку все обычные файлы, но не активный workflow.
2. Агент сохраняет **идентичную полную копию** workflow в обычном пути, например
   `tools/github-workflows/build.yml`, и даёт **две** ссылки на рабочую ветку:
   прямую `raw.githubusercontent.com` (откуда копировать) и `/edit/` на
   `.github/workflows/build.yml` (куда вставлять). См. «Формат ответов».
3. Пользователь открывает raw-ссылку, нажимает `Ctrl+A`, затем `Ctrl+C`.
   Нельзя копировать только видимый фрагмент из встроенного просмотрщика: длинный
   файл может быть показан не полностью.
4. Пользователь открывает `.github/workflows/build.yml` в **той же рабочей ветке**,
   в GitHub editor нажимает `Ctrl+A` → `Delete` → `Ctrl+V`, затем делает commit
   только в рабочую ветку, никогда не в `main`.
5. Агент обязан после commit проверить совпадение SHA-256 и размера активного workflow
   с копией в `tools/`, затем проверить успешный GitHub Actions run.
6. Только успешная сборка даёт APK для реального теста. Merge PR не требуется и не
   должен выполняться до окончания всех проверок и доработок.


### Юридические информационные условия

- Для приложений о здоровье, питании, активности и самочувствии при первом запуске
  показывать обязательное окно принятия условий. Формулировать, что данные имеют
  справочный характер, не заменяют квалифицированного специалиста и не предназначены
  для диагностики или лечения. Не обещать юридически невозможное «полное снятие
  ответственности».
- Отказ от условий должен блокировать использование. В Android закрытие приложения
  делается через нативный JavascriptInterface (`finishAndRemoveTask()`), а не через
  ненадёжный `window.close()`.


### Локальный голосовой помощник и модели

- Для массового приложения сначала реализовать цепочку «голос → текст → локальные правила →
  предварительный просмотр → подтверждение», не записывать распознанные данные автоматически.
- Локальная модель не имеет облачных лимитов запросов и после загрузки не требует VPN,
  Интернета, регистрации или API-ключа. Не использовать регистрацию для обхода лимитов
  облачных провайдеров.
- Облачный BYOK-режим (появился в 0.3.5) по решению пользователя от 06.08.2026 —
  ТОЛЬКО временный тестовый стенд сценариев будущего локального ИИ, в UI помечен
  «🧪 эксперимент». Он не должен становиться обязательным ни для одной функции:
  приложение обязано полностью работать без интернета, ключей и регистрации.
  Стратегическая цель — нейросеть на устройстве; при её появлении облачный режим
  сокращается или удаляется по решению пользователя.
- Модели хранить отдельно от APK: выбор лёгкой / продвинутой модели, собственное
  зеркало при разрешённом перераспространении, SHA-256 и ручной импорт файла.
- Перед публикацией проверить лицензию именно выбранного checkpoint, коммерческое
  распространение, NOTICE/атрибуцию, требования магазина, разрешение микрофона и
  политику приватности.


### Защита инициализации интерфейса

- После изменения HTML обязательно проверять, что все функции, передаваемые в
  `addEventListener`, существуют, а все ожидаемые ID присутствуют в разметке.
  Одна `ReferenceError` в `init()` прерывает последующие обработчики и может
  одновременно сломать тему, экспорт, импорт, сброс и настройки уведомлений.
- Для критичных элементов использовать безопасный helper привязки и отдельный
  быстрый тест инициализации интерфейса без Android-сборки.
- Помнить, что `document.querySelectorAll` возвращает NodeList, а не Array:
  у NodeList есть `.forEach`/`.length`, но НЕТ `.some/.map/.filter` — вызов роняет
  `init()` (красный баннер «… is not a function» и несвязанные нижние обработчики,
  как в краше 0.3.5 на входе). Хелпер `$$` в FitFlow обязан возвращать
  `Array.from(...)`; тест `test-ui-init.js` проверяет это как регресс-защиту.
  Ошибка в JS-стандартах «у коллекции есть forEach — значит, есть и some» —
  одна из самых коварных: в Node-среде тестов querySelectorAll обычно застаблен
  массивом или пустым списком, поэтому баг проявляется только на устройстве.

## Версия библиотеки — часть API (урок 0.9.15)

Первая сборка 0.9.15 упала на шаге `Build APK`. Код был логически верным и
написан строго по официальной документации Health Connect, но документация
описывает **актуальную** версию библиотеки, а проект собирается с
`androidx.health.connect:connect-client:1.1.0-alpha07` (январь 2024).
`HealthConnectFeatures` и `HealthPermission.PERMISSION_READ_HEALTH_DATA_IN_BACKGROUND`
появились только в `1.1.0-alpha09` — для нашей сборки это несуществующие
символы.

**Правило:** перед использованием нового класса или константы из внешней
библиотеки сверить, в какой версии он появился, и сравнить с версией,
закреплённой в `tools/github-workflows/build.yml`. Страница релизов библиотеки
даёт это одной строкой; JDK в песочнице нет, поэтому компилятор такую ошибку
не поймает — она проявится только красной сборкой.

**Второе правило — «обновить библиотеку» не бесплатно.** Очевидное решение
(поднять версию) здесь ломало другое: в `1.1.0-alpha12` поле `metadata` у
записей стало обязательным, а его конструктор — внутренним, и наш
`insertWorkoutSession` перестал бы компилироваться; alpha11+ дополнительно
требует `compileSdk 35`. Обновление библиотеки — отдельная задача с отдельной
проверкой, а не строчка в чужой версии. В 0.9.15 обошлись без него: разрешение
проверяет системная служба Health Connect, а не клиентская библиотека, поэтому
хватило литерала в манифесте и проверки `Build.VERSION.SDK_INT >= 35`.

**Что стережёт повтор:** тест в `test-ui-init.js` запрещает обращения к
`HealthConnectFeatures`, `HealthPermission.*` и `.features` в коде (не в
комментариях) `HealthConnectHelper.kt`, а второй тест посимвольно сверяет
строку разрешения — литерал больше не может тихо разойтись с платформенным
значением.

## Нативный код держать вне workflow (проверено в 0.8.27)

Проблема, которая долго тормозила разработку FitFlow: весь нативный Android-код
(Java/Kotlin) был вписан **внутрь** `.github/workflows/build.yml` как heredoc-блоки
(`cat > File.java << 'EOF'`). Файл разросся до 2251 строки. Из-за того, что GitHub App
без разрешения `workflows` не может пушить в `.github/workflows/`, **каждая правка
нативной части требовала ручной замены файла владельцем** — копирование содержимого
из зеркала через браузер на телефоне.

**Решение — вынести нативные исходники в обычный каталог репозитория:**

1. Создать каталог (в FitFlow — `android-native/`) и положить туда реальные
   `.java` / `.kt` файлы.
2. В workflow оставить один короткий шаг, который копирует их на место:
   ```yaml
   - name: Копировать нативные исходники (android-native/)
     run: |
       set -e
       DEST=android/app/src/main/java/<пакет>
       mkdir -p "$DEST"
       for f in A.java B.java C.kt; do
         [ -f "android-native/$f" ] || { echo "::error::нет android-native/$f"; exit 1; }
         cp "android-native/$f" "$DEST/$f"
       done
   ```
3. Проверить извлечение **побайтово**, а не на глаз: heredoc в YAML отбит отступом
   (в FitFlow — 10 пробелов), при снятии которого легко потерять строки, состоящие
   из одних пробелов. Сравнивать `[l[N:] for l in body]` с готовым файлом построчно.
4. Перевести автотесты, которые искали нативные строки в workflow, на объединённое
   чтение «workflow + все файлы каталога» — иначе проверки регресса молча исчезнут:
   ```js
   function readBuildBundle() {
     let out = fs.readFileSync('tools/github-workflows/build.yml', 'utf8');
     for (const f of fs.readdirSync('android-native').sort())
       out += '\n' + fs.readFileSync('android-native/' + f, 'utf8');
     return out;
   }
   ```

**Результат:** `build.yml` 2251 → 481 строка; правки нативного кода идут обычным
пушем. Ручная замена workflow нужна только при изменении самого workflow.

**Вывод для новых проектов: никогда не встраивать исходный код в YAML workflow.**
Workflow должен только собирать, а код — лежать в репозитории файлами. Это даёт
подсветку синтаксиса, нормальный diff, работающий поиск и, главное, снимает
зависимость от ручных действий владельца.

## Границы доступа AI-агента (проверено 2026-08)

Агент работает под токеном GitHub App с ограниченными правами. Что из этого следует:

- Пуш в `.github/workflows/**` — **запрещён** (нет разрешения `workflows`).
- `gh workflow run` / `workflow_dispatch` — **403**, запускать нельзя.
- Сборка при этом запускается **на `push` в любую ветку** — значит обычный коммит
  агента её и стартует, ручной запуск не нужен.
- Права нельзя расширить со стороны пользователя: они заданы платформой, а не
  настройками репозитория.
- **Агент не должен принимать токены, пароли и одноразовые коды в переписке.**
  Секреты (например, `KEYSTORE_BASE64`) добавляет только владелец через
  Settings → Secrets and variables → Actions.

Поэтому архитектуру CI надо строить так, чтобы всё изменяемое лежало **вне**
`.github/workflows/`, а сам workflow оставался максимально тонким и стабильным.

## Как исключить ручные действия владельца в CI (итог 0.8.27–0.8.28)

Раздел отвечает на прямой вопрос: **что нужно сделать, чтобы от разработчика больше
не требовалось ни ручной замены `build.yml`, ни ручного запуска Run workflow.**

### Две разные ручные операции — и обе устранимы

| Ручное действие | Почему возникало | Чем снимается |
|---|---|---|
| Замена `build.yml` через браузер | агент не может пушить в `.github/workflows/**` | вынести из workflow всё изменяемое |
| Нажатие «Run workflow» | привычка запускать сборку вручную; `workflow_dispatch` агенту недоступен (403) | триггер `on: push` в любую ветку |

### Правило 1. Workflow — тонкий и неизменяемый

Ручная замена нужна ровно тогда, когда меняется сам файл workflow. Значит, задача —
довести частоту его изменений **до нуля**. Всё, что меняется от версии к версии,
обязано лежать вне `.github/workflows/`:

- нативные исходники → `android-native/` (сделано в 0.8.27, `build.yml` 2251 → 480 строк);
- патчи и правки конфигов → отдельные скрипты в `tools/`, вызываемые одной строкой;
- версии и номера сборок → `version.txt` и `github.run_number`, а не константы в YAML;
- списки файлов для копирования → цикл по каталогу, а не перечисление имён.

Проверка зрелости: *«если завтра понадобится изменить нативный код, придётся ли
трогать `build.yml`?»* Если да — вынести ещё один кусок.

**Антипаттерн (был в FitFlow до 0.8.27):** исходный код внутри YAML через
`cat > File.java << 'EOF'`. Ломает подсветку, diff, поиск и создаёт ручную работу.

### Правило 2. Сборку запускает push, а не человек

В workflow должен быть триггер, который срабатывает от обычного коммита:

```yaml
on:
  push:
    branches: ['**']      # любой push стартует сборку — ручной запуск не нужен
  workflow_dispatch:       # оставляем только как запасной вариант для владельца
```

Проверено: коммиты агента (`b7ec209`, `26965bf`) стартовали сборку сами, без участия
владельца. `workflow_dispatch` агенту недоступен (403) и нужен исключительно как
ручная страховка — **штатный путь запуска — это push**.

### Правило 3. Зеркало workflow для редких неизбежных правок

Пока `.github/workflows/build.yml` изменить всё же нужно, актуальная копия держится
в `tools/github-workflows/build.yml`. Агент правит зеркало, владелец один раз
копирует его содержимое. Обязательная проверка идентичности после замены:

```bash
cmp <(git show HEAD:.github/workflows/build.yml) \
    <(git show HEAD:tools/github-workflows/build.yml) && echo "идентичны"
```

Различие в `wc -l` на одну строку — это отсутствие финального перевода строки,
а не расхождение содержимого; ориентироваться нужно на `cmp`, а не на счётчик строк.

### Правило 4. Проверять результат без участия владельца

Просить владельца «посмотреть, собралось ли» не нужно — статус читается командами:

```bash
gh run list --branch <ветка> --limit 5 --json databaseId,status,conclusion,headSha
gh run watch <ID> --exit-status --interval 20
gh release list --limit 2
```

### Что осталось ручным осознанно

- **Секреты** (`KEYSTORE_BASE64`, пароли подписи) — только владелец, через
  Settings → Secrets and variables → Actions. Агент не принимает их в переписке.
- **Проверка APK на живом устройстве** — скачивание файлов в песочнице недоступно.
- **Замена самого workflow** — редкий случай; по плану остался один раз, на шаге
  release-подписи.

**Вывод:** ручные действия исчезают не из-за расширения прав агента (их расширить
нельзя), а из-за архитектуры: тонкий стабильный workflow + весь изменяемый код
в обычных файлах + запуск сборки обычным push.
