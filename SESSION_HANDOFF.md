# Передача разработки FitFlow

Этот файл нужен только на случай, если текущий диалог Arena нельзя продолжить.

## Что передать новому агенту

1. Открыть и прочитать `AI_GUIDE.md`, `PROJECT.md` и этот файл.
2. Выполнить `node test-parser.js` (200+ проверок, ожидается `ALL TESTS PASSED`), `node test-ui-init.js` (240+, ожидается `UI INIT CHECK PASSED`) и `node test-food-db.js` (аудит базы 960+ ключей, ожидается `FOOD DB CHECK PASSED`).
3. Сначала проверить `git status` и `git log --oneline`.
4. Не выполнять Merge PR до завершения всех задач пользователя.
5. Номер версии приложения живёт в `version.txt` в корне репозитория; workflow сборки читает его сам (с 0.2.5). Чтобы выпустить новую версию, не нужно править build.yml — только `version.txt` и код.
6. Помнить «Принцип обратной связи» из AI_GUIDE.md: комментарии пользователя — предложения к обсуждению; отвечать по каждому пункту, спорить аргументированно, если есть решение лучше.

## Актуальный процесс релиза (с 0.2.5)

**Обычная версия (код/HTML/CSS/JS, а также смена номера версии):**
1. Агент правит код, обновляет `version.txt` + `package.json` + `FITFLOW_VERSION` в app.js, коммитит и пушит в рабочую ветку.
2. GitHub Actions сам читает `version.txt`, собирает `FitFlow-v<версия>-debug.apk` и публикует релиз. Пользователю ничего менять не нужно.
3. Агент проверяет успешный run через `gh` и присылает готовые ссылки:
   - APK: `https://github.com/Help-yourself-dvp/LifeFlow-Fitness/releases/download/v<версия>-build<N>/FitFlow-v<версия>-debug.apk`
   - страница релиза: `.../releases/tag/v<версия>-build<N>`

**Нативная версия (Gradle-зависимости, Capacitor-плагины, MainActivity, виджет, иконки):**
1. Агент коммитит код + обновлённую копию `tools/github-workflows/build.yml`, но активный workflow не трогает.
2. Агент присылает шаблон ответа (см. ниже); пользователь вручную заменяет `.github/workflows/build.yml` содержимым raw-файла и коммитит в рабочую ветку (Commit message любое, подходит стандартное `Update build.yml`).
3. Замена сама запускает сборку; агент проверяет SHA-256/размер и даёт ссылки на APK.

**Шаблон ответа при изменении build.yml:**

> **Финальная тестовая APK <версия>**
> Подготовленный workflow содержит все доработки версии <версия>. Активный workflow на GitHub пока содержит <предыдущая версия>, поэтому нужно вручную заменить workflow ещё один раз.
> **Готовый файл:** [raw.githubusercontent.com/.../tools/github-workflows/build.yml]
> **Редактор active workflow:** [github.com/.../edit/arena/<ветка>/.github/workflows/build.yml]
> Порядок: `В raw-файле: Ctrl + A → Ctrl + C` `В редакторе: Ctrl + A → Delete → Ctrl + V`
> Перед коммитом проверьте: `Ветка: arena/<ветка>` `Ключевые маркеры новой версии в файле`
> Не выбирайте `main` и не нажимайте **Merge pull request**.
> Контрольные данные: `SHA-256: <hash>` `Размер: <байт>`
> После ручного коммита напишите «готово» — агент проверит сборку и даст точную ссылку на APK.

## 0.3.31 — сессия: голос-проверка, яйца/колбаса, сворачивание, обоснование локального ИИ

1. **«Не вижу, что распознано» = отсутствует шаг подтверждения.** Голос писал в скрытое поле с быстрым toast — классика «невидимого результата». Рецепт: результат голоса всегда через экран предпросмотра (умный ввод уже умел), сохранение по явной кнопке. Веб-фолбэк SpeechRecognition унифицирован тем же путём — единый вход onVoiceInputResult.
2. **Числительные в родительном падеже отдельны.** «из двух яиц» не ловится NUMBER_WORDS («два») — для доменных конструкций нужны свои мини-карты (eggPortionCount: двух/трёх/четырёх/…). Универсальный numberWordLead трогать не стали.
3. **Порционные дефолты — семействами, не по одному.** Кусок=100 г честен для торта и ложен для колбасы; правим семейством с кейсом пользователя и автотестом (хлеб 40 г → колбасные 45 г). Сыр «по кускам» намеренно не тронут (нет кейса — гард не-нагромождения для правил).
4. **Сворачивание > карусели для дневного потока.** Карусель прячет контент и конфликтует с вертикальным скроллом; кандидат на неё — галерейные блоки (медали). Порог «4+ = свёрнуто» уважает и короткие дни (никаких лишних тапов).
5. **Корень «левого текста Отмены» — display:inline-flex без justify.** Лечится ОДНИМ правилом на контейнер диалогов, а не по диалогам.
6. **Скроллбар в Android WebView — только мельком.** Визуальное «прокручиваемо» дают градиент-южная тень + полоса в цвет темы (MutationObserver ставит класс). Не ручка — аффордансов не обещаем.
7. **Дремлющий JS к нативному модулю:** вся ветка строго проверяет Capacitor.Plugins.<Name>, без модуля — честные тексты и скрытые кнопки; старые «local://»-заглушки принудительно признаются недействительными. Два ложных аффорданса litert-стаба (имитатор скачивания, фальш-подключение файла) признаны и убраны по принципу 7.
8. **Локальный ИИ как конструктор:** плагин в репо (Kotlin, LiteRT-LM 0.12.0, minSdk 24), подключение = 2 правки build.yml инструкцией LOCAL_AI_PATCH.md (npm install ./plugins/... + sed minSdk). Один контекст buildAiSystemContext на оба канала (облако=устройство); сбой нейросети → эксперт под ошибкой.

## 0.3.32 — сессия: супы, гарантия не-молчания, честные счётчики, скролл-семейство

1. **Ответ на «продукт будет сырым всегда» — архитектурный, а не обещательный.** Регулярный парсер всегда имеет длинный хвост; чинить «по дому каждый раз» бесконечно нельзя. Честный ответ строится из трёх частей: (а) конкретную дыру чиним семейством + автотест (супы), (б) 100%-я гарантия — непонятное ВСЕГДА видно («⚠️ Не разобрал», parseMealTextDetailed/unparsed), (в) полное понимание речи — локальная Gemma (0.4.x). Это повторяемая формула ответа на подобные боли.
2. **Гард цельного ключа — только с пробелом.** lookupProduct('щи со свининой') находит 'свинина' подстрокой — проверка «вся фраза есть в базе» обязана требовать составной ключ (`key.indexOf(' ') !== -1`), иначе комбо-правило молча отключится.
3. **Орденок правил важен внутри семейства.** «Борщ со сметаной» — сметана по COMPANION_GRAMS (20 г), а не по SOUP_MEAT_GRAMS (50 г): приправы раньше мяса. Штучная добавка — естественный путь 1 шт. Каждая ветка — свой автотест.
4. **Счётчик = единица смысла пользователя, не структуры данных.** state.food.items.length — продукты; «записью» пользователь называет приём пищи. Выводим оба числа с именами («2 приёма · 11 позиций») — не 「переименовать」, а честно показать обе размерности.
5. **gh api contents по умолчанию читает DEFAULT-ветку (main).** «Расхождение» зеркала build.yml оказалось чтением не того ref (?ref=arena/... обязателен). Урок: любые сверки с GitHub — с явным ref нашей ветки.
6. **Патч-файлы имеют версии.** Просьба «ещё чуть больше» при неприменённом патче = обновить сам патч и честно пометить в нём, что прежние значения ни в одной сборке не жили. Не делать вид, что «стало лучше» от кода.
7. **UI-тексты — тоже код правдивости.** Справка «голос появится позже» устарела молча после включения RecognizerIntent — проверять справочные тексты при смене фич (теперь это часть ui-init через якорь на запрет старой фразы).
8. **Скролл-дифференциация оттенком одного токена** (primary 30% vs 55%), а не разными цветами — единое семейство без «серой против зелёной»; тоньше основная (5 px) против окон разбора (6 px).

11. **Фото-итерация (0.4.0): нейронка — глаза, парсер — истина.** Снимок НЕ

22. **У маленькой зрячей модели две лени: повторять и «весить порциями»
   (0.4.10).** Полевая тарелка: каждый компонент получил «1 порцию» (по 200 г
   из базы → 1,2 кг еды) и один овощ назван дважды в двух формах. Лечение в
   ДВУХ независимых слоях: промпт запрещает «порцию» и повторы и даёт якоря
   граммов (классовая ошибка, чинится классом «тарелка»), а парсер складывает
   одинаковые позиции суммой с честной пометкой — страховка остаётся честной
   даже при старом промпте. Общее правило: за «лентяйством» модели идёт
   детерминированный слой, который делает вход дороже-жёстче, а не верит ему.
21. **«Собрать объект ≠ сохранить объект»: молчаливая потеря данных (0.4.9).**
   normalizeDailyHistory конструировал запись дня и… отбрасывал её (в Map
   byDate ничего не клали), а вызывался при каждом saveState — dailyHistory
   был [] всегда; баг не виден ни в UI сегодняшнего дня, ни в тестах (их не
   было на историю), всплыл только когда владелец открыл статистику за вчера.
   Два правила из урока: (а) функции-мутаторы накопителей превращать в ЧИСТЫЕ
   с node-регрессом («положил 2 — получил 2»), где scope-стейт не мешает
   проверке; (б) про уже потерянное говорить прямо, с перечислением, что
   уцелело (журналы тренировок/веса/сна хранят даты сами — они и стали
   честным фоном статистики в дни без сводки). Побочный урок парсера (P11):
   lookupProduct-угадайка по префиксу отлично маскируется под составной ключ
   («маслом сыром»→«масло») — доказательство «настоящего» ключа только
   равенство числа слов ввода и ключа.
20. **Тяжёлая модель в RAM + тяжёлая внешняя активити = выстрел в себя (0.4.8).**
   Полевая картина «после ✓ вышвырнуло на главный экран»: capture-интент и
   камера исправны, но с ~3 ГБ модели в RAM наш процесс — первый кандидат на
   выгрузку под чужую камеру; возврат = холодный старт, change с файлом умирает
   вместе со старым процессом (WebView ValueCallback смерти не переживает —
   в отличие от классического нативного FileProvider-паттерна). Почему раньше
   не ловили: первые фото до 0.4.2 делались до прогрева модели, а потом полевые
   прогоны шли через лёгкую галерею. Формула: перед выходом во внешнюю активити
   под большой нативной памятью — освободить RAM (огненно-забыточный
   unloadModel без await: жест обязан остаться синхронным; подъём обратно —
   обязанность downstream-пайплайна с видимым этапом). И «не молчать»
   распространяется на смерть процесса: метка в localStorage перед пикером +
   три пути гашения (change / возврат видимости без change = отмена / давность)
   + честное сообщение на следующем старте, ЧТО именно потерялось.
19. **capture-интент — единственно надёжный путь камеры (0.4.7).** Четыре
   итерации одного урока: capture= прячет галерею → убрать → пикер без
   камеры (declared!) → манифест → всё равно нет (granted!) → runtime-запрос
   по делу → оболочка владельца пикера камеры ЛИШЕНА совсем. Финальная схема:
   capture-инпут (камера, разрешение интенту не нужно — потому до 0.4.2
   работало) + отдельный инпут (галерея). Параллельный откат: GPU (0.4.6) на
   поле медленнее CPU — бенч производителя ≠ устройство владельца; «улучшения»
   по просьбе владельца откатываем с памяткой, не отстаиваем.
18. **declared ≠ granted: WebView-пикер видит только выданное (0.4.5).**
   Манифест 0.4.3 добавил CAMERA permission, но пункт «Камера» не появился:
   системный выбор фото смотрит на GRANTED, а WebView runtime-запрос сам не
   делает. Разрешение спрашивается ПО ДЕЙСТВИЮ (нажатие 📷, не старт) через
   Capacitor Permission API плагина. Параллельный урок: каждое «принято за 1»
   без слов пользователя должно носить честную пометку («упаковка = 1 шт?»).
17. **Правка намерения ломает разрешение — проверять манифест (0.4.3).**
   Убрание `capture=` открыло галерею, но спрятало пункт «Камера»: WebView
   показывает его ТОЛЬКО при объявленном CAMERA permission в манифесте, а
   манифест генерируется в CI-шаблоне — правка легла в зеркало workflow
   (пользователь применяет файл). Побочно: потребность молчания воды закрыта
   стражем — КАЖДЫЙ канал ввода (еда/вода/активность) имеет право на свой
   «не молчать», не только еда (дыра найдена полевым фото, прогон обязателен).
16. **Зрение считает, весит плохо — деление труда с базой (0.4.2).** Полевой
   кейс «связка 5 бананов = 2000 г»: маленькой зрячей модели счёт предметов
   даётся, оценка веса — нет. Вывод: штучное просить КОЛИЧЕСТВОМ, а граммы
   достаёт детерминированная база (per: 'шт'). Якоря веса в промпте помогают,
   но не заменяют принцип «правдивость чисел — у кода».
15. **Температура — свойство ЗАДАЧИ, не сессии (0.4.2).** Экстракция с фото
   (0.2 против фантазий) и разговор (0.7 по просьбе владельца) требуют разных
   температур на ОДНОМ движке: пересобирать диалог дёшево, но ОБЯЗАТЕЛЬНО
   возвращать чатовую после (ответ/ошибка/таймаут) — иначе спящая
   рассинхронизация, уже битая однажды (0.3.38, lastTemperature).
14. **`capture=` в WebView решает, чем пользоваться (0.4.2).** Атрибут жёстко
   форсирует камеру и прячет галерею; без него системный пикер Android сам
   предлагает камеру/галерею/файлы. Запрос «фото из галереи» лечится удалением
   атрибута, а не новым кодом — сначала проверить декларативный слой.
13. **Проверка «честного отказа» должна быть node-прогоном, а не чтением (0.4.1).**
   Проверка ответа модели «нет» (нет еды на фото) использовала `\b` — в JS
   граница слова только ASCII, кириллицу не видит; плюс двойной бэкслеш в
   литерале из heredoc-правок. Итог: ветка не срабатывала НИКОДА, и это не
   ловилось глазом. Правило: каждая регэксп-проверка на русском тексте —
   с прогоном «матчит/не матчит» в node до коммита (у нас «нетто 200 г»
   как раз ложный случай, который ловит такой прогон).
12. **Тост — не канал для этапов и ошибок (0.4.1).** Полевая жалоба «не успеваю
   почитать, и ничего не происходит» раскрутилась в два дефекта: (а) входная
   точка (камера ИИ-поля) осталась на тост-заглушке эпохи «только облако» —
   при добавлении нового флоу искать ВСЕ старые входные точки функции, а не
   только новую кнопку (grep по тексту тоста нашёл её мгновенно); (б) этапы
   долгого процесса нельзя класть в исчезающий тост — только в панель на
   экране, тосты длинных инструкций — 6 с (toast(message, ms)).
11. **Арифметику за LLM считает JS (0.4.1).** Кейс «2300 ккал — это немного
   БОЛЬШЕ нормы 2500»: маленькая модель ненадёжна даже в сравнении двух чисел.
   Любые конкретные числа из контекста отдавать ей с ГОТОВЫМ вердиктом
   («МЕНЬШЕ цели на 200, осталось 200»), а в системный промпт — прямой запрет
   выполнять арифметику самой. Правдивость расчётов > правдоподобие текста.
10. **Стриминг лечит восприятие медленной нейросети (0.3.39).** Боль «3 минуты
   без результата» — это не только латентность, но и молчание UI: этапы

   notifyListeners → Capacitor addListener) превращают чёрный ящик в процесс.
