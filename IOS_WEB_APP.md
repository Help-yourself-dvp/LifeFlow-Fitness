## 1. Короткий ответ на вопросы владельца

> **Статус на 0.9.56:** веб-версия работает и опубликована —
> **https://help-yourself-dvp.github.io/LifeFlow-Fitness/** (owner включил
> Pages 02.10.2026, статус сборки «built»). Шаги P1 (каркас) и P2 (честная
> деградация без «мёртвых» кнопок) сделаны; Android-версия не изменилась.

1. **Веб-версия делается не «с нуля».** FitFlow и так написан на чистых
   HTML/CSS/JS и уже открывается в браузере (см. README, «Как смотреть
   приложение в браузере»). Задача — не переписать приложение, а «докрутить»
   его до устанавливаемого приложения: манифест, служебный кэш (service
   worker), иконки, публикация по HTTPS. Это и есть PWA.
2. **Отдельный репозиторий для веб-версии не нужен.** Один код — две
   доставки: одни и те же файлы (`index.html`, `style.css`, `app.js`,
   `sqlite-bundle.js`, `assets/`) идут и в APK (Capacitor), и на сайт
   (GitHub Pages). Правите код один раз в одном месте.
3. **Правки, полезные iPhone, появляются на iPhone сразу** — после
   обновления страницы/перезапуска иконки на «Домой». Для Android всё как вы
   привыкли: новая сборка APK в GitHub Actions и установка поверх старой.
4. **Ядро сохраняется полностью:** вода, питание, парсер 960+ продуктов,
   «Комбо», «Мои блюда», «Мои продукты», статистика, силовой дневник,
   тренировки, вес, самочувствие, медали, профили, темы, экспорт/импорт
   копии файлом. **Теряются** те вещи, которые опираются на нативные API
   Android: фоновые напоминания, автоматические шаги/сон с часов, виджет
   рабочего стола, локальная нейросеть Gemma, кнопка на часах Wear OS
   (подробно — § 4, обходы — § 5).
5. **Синхронизация между устройствами реальна** и без «недоступных в РФ»
   сервисов. Ваш вариант — приватный репозиторий GitHub как хранилище
   файлов — рабочий; рядом есть Яндекс.Диск и совсем «без сервисов» —
   файл/AirDrop (§ 6). Это шаг 2, после работающей веб-версии.

## 3. Как это будет выглядеть в работе

### 3.1. Один раз на iPhone

1. Открыть адрес веб-версии в **Safari**.
2. Кнопка «Поделиться» → **«На экран „Домой“»** → «Добавить».
3. Дальше запускать **только с иконки на «Домой»**, а не из вкладки Safari —
   это важно (§ 3.3).

Никаких Apple ID, аккаунтов, TestFlight и 99 $/год. Приложение работает
офлайн (файлы кэшируются), данные лежат на телефоне.

### 3.2. Дальше — как обычное приложение

- Иконка на «Домой», открывается полноэкранно, без адресной строки.
- Вода/еда/тренировки/статистика — как на Android, интерфейс тот же.
- Копия файлом — «Настройки → Экспорт»: файл уходит в «Файлы → Загрузки»,
  оттуда его можно отправить себе в мессенджер/AirDrop.
- Обновление веб-версии — само (взял свежие файлы из сети при запуске),
  новая иконка не нужна. APK обновляется как сейчас.

### 3.3. Три особенности iOS, о которых надо знать заранее

1. **Установленное веб-приложение и Safari — разные хранилища.**
   Данные вкладки Safari не видны приложению с «Домой» и наоборот. Порядок
   такой: сначала установили на «Домой», потом начали вводить данные. Если
   начали в Safari — выгрузите копию файлом и импортируйте её уже в
   установленном приложении.
2. **Очистка хранилища.** Safari стирает данные сайтов, которые 7 дней не
   открывали. **На установленные веб-приложения это правило не действует** —
   у них свой счётчик и своя квота. Но привычка «копия файлом раз в месяц»
   всё равно остаётся правильной: удаление иконки или «Очистить историю и
   данные сайтов» данные уносят.
3. **Фон на iOS не работает.** Как только приложение ушло с экрана, iOS его
   приостанавливает: ничего не обновляется, ничего не «звонит» по таймеру.
   Поэтому на iPhone нет фоновой синхронизации и фоновых напоминаний —
   только при открытии (это уже учтено в логике приложения: сброс дня при
   возврате из фона, 0.9.53).

## 4. Что на iPhone в веб-версии не получится в принципе

Это не «мы не умеем», это ограничения iOS для сайтов и веб-приложений.
Честно и по пунктам:

1. **Виджет рабочего стола.** Safari-приложение не может добавить виджет на
   домашний экран iOS. Только нативное приложение (отдельная сборка под
   Apple и платная подписка разработчика). Обхода нет.
2. **Автоматические шаги и сон с часов/телефона.** Apple Health (HealthKit)
   закрыт для сайтов: веб-страница не имеет доступа к шагам, сну,
   тренировкам, весу. Обход — только через приложение «Команды» (§ 5.1).
3. **Напоминания при закрытом приложении.** У iOS-веб-приложений нет
   локальных уведомлений по расписанию. Push-уведомления технически есть
   (iOS 16.4+), но **требуют постоянного сервера-отправителя** — это ломает
   принцип «никаких серверов» и наших данных нигде. Обход — календарь и
   «Команды» (§ 5.2).
4. **Работа в фоне.** Никакого обновления в полночь, никакой фоновой
   синхронизации, никаких «тихих» напоминаний. Данные всегда актуальны на
   момент открытия приложения.
5. **Нейросеть Gemma на устройстве.** Это нативный Android-плагин
   (`plugins/fitflow-local-ai`, LiteRT-LM). На iOS он не собирается, а в
   веб-версии движка нет вовсе. Остаётся облачный ИИ по вашему ключу — и
   только если провайдер доступен из браузера.
6. **Кнопки на часах.** Аналога «+ 250 мл» с Wear OS для Apple Watch у
   веб-приложения нет.
7. **«Поделиться в FitFlow» из других приложений.** iOS не умеет отправлять
   данные из сторонних приложений в веб-приложение. Копировать текст
   придётся вручную (вставить в поле ввода еды).

Что при этом **остаётся полностью рабочим** (проверено по коду): вся вода и
питание, парсер фраз, «Комбо», «Мои блюда/продукты», журнал распознаваний,
статистика и сравнение периодов, активность (ручной ввод), силовой дневник
с шаблонами и таймером отдыха, вес, самочувствие, медали, профили, темы,
экспорт/импорт, онлайн-индикатор, чтение базы Open Food Facts для сканера.

## 5. Обходы без сторонних сервисов (всё внутри iPhone)

### 5.1. Шаги/сон/вес из Apple Health — приложением «Команды» (Shortcuts)

**Проверено 02.10.2026 по документации и опыту (важно для P6):**

- Автоматизация «Команды» → **Time of Day** с переключателем **«Run
  Immediately»** (не «Run After Confirmation») запускается **сама, без единого
  нажатия** — пользователю ничего делать не нужно. Именно поэтому вариант
  рабочий «на годы», а не «на неделю».
- **НО: доступ к данным Здоровья требует разблокированного телефона.** Если в
  момент срабатывания автоматизации iPhone заблокирован, чтение образцов
  Health падает с ошибкой. (Действие `Allow Running When Locked` снимает
  требование разблокировки для самой автоматизации, но не для доступа к
  Здоровью.)
- **Практический вывод — время срабатывания:** утро, когда телефон почти
  наверняка в руках (пробуждение/снятие будильника). Лучший триггер —
  **«Alarm» → будильник выключен** (в списке разрешённых к автоматическому
  запуску) или Time of Day ~08:00.
- **Заодно решается вопрос «шаги с 23:00 до 24:00»**: утренняя автоматизация
  читает **итог за вчерашний день целиком** (Здоровье суммирует весь день,
  включая последний час), поэтому «хвост» дня не теряется. Днём можно добавить
  ещё 2–3 автоматизации (13:00, 18:00, 22:00) — они дают предварительные
  значения за сегодня; каждая срабатывает только если телефон в этот момент
  разблокирован, и это нормально: следующая перезапишет число.
- **Apple Watch шаги входят в тот же итог**: Здоровье сливает iPhone и часы
  (а для Zepp/Amazfit — если в приложении-компаньоне включена запись в
  Здоровье), поэтому одно число покрывает все источники.
- Триггер **«Apple Watch Workout»** (тренировка завершена) тоже разрешён к
  автоматическому запуску — им можно отправлять тренировку сразу после её
  окончания, без ожидания вечера.
- Запасной вариант (если телефон никогда не разблокирован в выбранное время):
  в приложении есть кнопка «Синхронизировать» — но цель как раз в том, чтобы
  она не требовалась.

«Команды» умеют читать образцы Health (шаги, сон, тренировки, вес) и делать
HTTP-запрос. Дальше два пути:

- **С синхронизацией (шаг 2):** персональная автоматизация «в 23:00» читает
  шаги за день и кладёт их в то же хранилище, что и синхронизация
  (приватный репозиторий). Приложение подхватывает их при следующем
  открытии. Это ближайший аналог Health Connect, без нашего сервера.
- **Без синхронизации:** команда сохраняет число в «Файлы», вы раз в день
  открываете приложение и импортируете файл. Ручная работа — как вариант
  «на попробовать».

Честная оценка: полноценного автоматического шагомера, как на Android, у
веб-версии не будет. Это самый крупный функциональный минус веб-версии.

### 5.2. Напоминания — календарь или «Команды»

- **Календарь (`.ics`).** Приложение может выгрузить файл с событиями и
  сигналами (вода каждые 2 часа, приём курса по расписанию). Один раз
  импортировали в «Календарь» — напоминания работают системно, офлайн, без
  серверов. Минус: при изменении расписания файл надо импортировать заново
  (можно завести отдельный календарь «FitFlow» и очищать его целиком).
- **«Команды».** Автоматизация «в 21:00 → показать уведомление „Запиши воду
  в FitFlow“». Работает локально, настраивается один раз на телефоне.

### 5.4. Исследование (запрос владельца 02.10.2026): фоновые напоминания через web-push

Владелец видел рабочий пример: веб-приложение (то же GitHub + ИИ) присылает
уведомления на iPhone и Android **при выключенном экране и закрытом
приложении**. Это действительно возможно — механизм называется **Web Push**.
Но у него есть обязательная деталь, из-за которой нельзя «пока не разбираться»:

**Как это устроено (и почему не «локальные» уведомления):**

1. Приложение (служба `sw.js`) один раз подписывается на push и получает
   адрес-подписку (endpoint) + два ключа шифрования.
2. **Сервер-отправитель** в нужное время шифрует короткое сообщение VAPID-ключом
   и отправляет его на endpoint.
3. Push-служба платформы (Apple APNs для iOS, FCM/Mozilla для Android)
   доставляет «звонок» на телефон даже при закрытом приложении.
4. Просыпается `sw.js` (обработчик `push`), показывает системное уведомление
   по тексту из сообщения. На iOS это работает **только** для приложения,
   добавленного на «Домой» (iOS 16.4+).

Итого: **нужен планировщик, который в нужный момент отправит push.** Это не
сервер с данными пользователя: сообщение может быть пустым по смыслу
(«пора отметить воду»), а все цифры остаются на устройстве. Но что-то, что
работает круглосуточно и умеет «разбудить» телефон, обязано существовать —
у iOS-веб-приложения нет локальных таймеров (в отличие от Android-версии,
где у нас свой `AlarmManager`).

**Варианты планировщика, доступные из РФ без карты:**

1. **Облачная функция с таймером** (Cloudflare Workers Cron Triggers, Яндекс
   Облако.Функции + таймер). Бесплатных лимитов достаточно с большим запасом:
   один push в час — это ~700 вызовов в месяц. Минус: разовая настройка
   в панели сервиса (10–15 минут), у Cloudflare возможны перебои доступа из РФ.
2. **GitHub Actions по расписанию** — так сделано **во втором приложении
   владельца** (подтверждено 02.10.2026), то есть схема проверена на практике.
   **Важное ограничение, о котором надо помнить:** задания по расписанию
   GitHub выполняет только из **ветки по умолчанию** (у нас `main`, а она —
   старый снимок; скрипт расписания обязан лежать именно там). Кроме того:
   задержки 5–30 минут, возможные пропуски при нагрузке и отключение
   расписания после 60 дней без активности репозитория.
   **Как это обойти в нашем проекте:** сам workflow-отправитель можно
   разрабатывать и тестировать в рабочей ветке, запуская его **обычным пушем**
   (триггер `on: push` работает), а расписание (`on: schedule`) включится само
   после финального переноса в `main`. Если напоминания нужны раньше — тот же
   скрипт отправки можно вызывать из другого планировщика (вариант 1 или 3).
   Отдельно: один общий планировщик означает, что у него лежат push-подписки
   пользователей (не их данные, но адреса доставки) — для «для себя» это
   нормально, для массового использования это уже сервис, и решать это надо
   отдельно (см. § 13).
3. **Внешний планировщик** (бесплатные сервисы cron-задач, дёргающие
   workflow через `repository_dispatch`). Требует PAT и третьего сервиса —
   лишняя сущность.

**Честные оговорки по iOS:** подписка может «отваливаться» (нужна перепроверка
при каждом запуске приложения), в фоне iOS не даёт считать время — «только
один push в час» контролирует отправитель, а не телефон; зато текст уведомления
может быть без цифр и данных.

**Решение владельца (02.10.2026):** тема не откладывается «в самый конец» —
она в списке обязательных шагов (P8) и разбирается сразу после основной базы,
когда уже понятно, как приложение ведёт себя на iPhone.

**Схема второго приложения владельца (проверена на Honor, 02.10.2026) — берём
её за основу для FitFlow:**

| Что | Где | Аналог в FitFlow |
|---|---|---|
| Отправитель по расписанию | `.github/workflows/push-sender.yml` в **публичном** репозитории (расписание GitHub читает из `main`) | новый workflow `push-sender.yml` в этом репозитории |
| Подписки устройств | **приватный** репозиторий данных, `data/push/<deviceId>.json` | либо приватный репозиторий P5, либо отдельный `lifeflow-fitness-data` |
| Секреты | ключ доступа к приватному репозиторию + приватный ключ VAPID — в Secrets публичного репозитория | так же; секрет добавляет только владелец |
| Отправка | Node-скрипт `scripts/push-sender.mjs`, пакет `web-push` | `tools/push-sender.mjs` (не попадает в APK и не мешает сборке) |

**Что обязательно учесть (сказано владельцем и подтверждается документацией):**

1. **Успешная проверка была из рабочей ветки, а расписание GitHub работает
   только из `main`** — значит, для FitFlow отправитель разрабатывается и
   проверяется в рабочей ветке (запуск обычным пушем), а расписание включается
   после финального переноса в `main`.
2. **Доставка на заблокированный iPhone ещё не подтверждена** — это главный
   неизвестный пункт P8. Поэтому план: сначала проверить на живом iPhone, потом
   обещать. Если окажется, что при заблокированном экране push не показывается,
   честный запасной путь — календарь `.ics` (P7).
3. Для iOS нужны: установленное на «Домой» приложение, разрешение уведомлений
   и **живая подписка**; подписка может «отваливаться» — приложение должно
   перепроверять её при каждом запуске и складывать заново (как в приложении
   владельца: перепроверка не чаще раза в 6 часов).
4. Дополнительно к push полезна автоматизация «Команды» → «Открыть FitFlow»
   (триггер **App**) — она подтянет данные в тот момент, когда пользователь сам
   открыл приложение.

## 6. Синхронизация между устройствами (шаг 2)

### 6.1. Чего мы не используем и почему

- **iCloud/Firebase/Supabase/Google Drive** — аккаунты, лимиты, часть
  недоступна из РФ, а данные уходят третьей стороне. Не наш путь.
- **Свой сервер** — противоречит принципу «нет серверов, нет подписки».
- **WebRTC напрямую между телефонами** — технически возможно, но требует
  ручного «рукопожатия» и работает только когда оба устройства открыты.
  Хрупко, не для ежедневного трекера.

### 6.2. Вариант A (рекомендуемый): приватный репозиторий GitHub как хранилище

Ваша идея рабочая. Как это устроено правильно:

1. **Отдельный ПРИВАТНЫЙ репозиторий только для данных.** Не этот: наш
   репозиторий с кодом публичный, данные туда попасть не должны.
2. **Ключ (fine-grained token)** — только к этому приватному репозиторию,
   права «Contents: Read and write», срок — «без истечения». Ключ хранится
   **только на устройстве** (в данных приложения), в код и в публичный
   репозиторий не попадает. В приложении — поле ввода ключа и кнопка
   «Проверить связь»; отозвать доступ можно одной кнопкой на GitHub.
3. **Файлы по устройству, а не один общий.** Каждое устройство пишет свой
   файл: `devices/iphone-<id>.json`, `devices/android-<id>.json`. Так
   **конфликтов не бывает по построению** — устройства никогда не пишут в
   один файл. При чтении приложение сливает все файлы в один профиль.
4. **Слияние по времени.** Для записей хранится время изменения; старое
   проигрывает новому. Если правки были на двух устройствах в разные дни —
   обе сохраняются, ни одна не «затирает» другую.
5. **Когда синхронизируется:** при открытии приложения, после сохранения
   (с задержкой) и по кнопке «Синхронизировать сейчас». Фоново — нельзя
   (iOS), поэтому при закрытом приложении данные не уезжают, но и не теряются.
6. **Плюсы:** бесплатно, без серверов, GitHub вы уже используете; история
   версий файлов сама является архивом копий. **Минусы:** ключ лежит на
   телефоне (защищён паролем/биометрией телефона и ограничен одним
   приватным репозиторием); GitHub должен быть доступен — как и сейчас для
   скачивания APK.
7. **Бонус:** тот же формат синхронизации смогут использовать APK на
   Android — телефон и iPhone начнут видеть одни и те же данные.

### 6.3. Вариант B: Яндекс.Диск (если хочется «российское и стабильное»)

REST API + OAuth, папка приложения на Диске. Работает из РФ без VPN, у вас
уже есть аккаунт. Минус: нужно зарегистрировать приложение (10 минут) и
проверить, что запросы идут из браузера (CORS) — проверяется на практике.
Схема та же: файлы по устройству + слияние.

### 6.4. Вариант C: совсем без сервисов

Копия файлом + AirDrop/мессенджер между устройствами, импорт вручную.
Плюс: ноль настройки. Минус: руками, легко забыть.

**Рекомендация:** начать с A (GitHub), потому что он не добавляет ничего
нового в вашу жизнь — это тот же GitHub, только второй, приватный
репозиторий. Если что-то не устроит — B меняется почти без переделки логики
слияния.

## 7. Один репозиторий или два? Как вносить изменения?

**Код — один репозиторий** (`LifeFlow-Fitness`), как сейчас.

- Веб-часть (`index.html`, `style.css`, `app.js`, `sqlite-bundle.js`,
  `assets/`) — общая для Android и iPhone. Изменили один раз — на iPhone
  прилетело сразу, на Android — после новой сборки APK.
- Android-натив (`android-native/*.java|kt`, `android-res/`, workflow) —
  живёт в том же репозитории, но на веб-версию не влияет вовсе.
- Добавлять «веб-специфичные» файлы (`manifest.json`, `sw.js`, иконки для
  iOS) будем аккуратно, чтобы сборка APK их не тянула (там Capacitor
  генерирует свои манифест и иконки).

**Второй репозиторий (приватный) появляется только на шаге синхронизации —
и это не репозиторий кода, а хранилище файлов данных.** Изменения
функционала в него вносить не нужно никогда: он просто «флешка в интернете».

Итог по вашему вопросу: **в несколько репозиториев код не разъезжается.**
Одна правка — одно место. Разная только «упаковка»: сайт обновляется сам,
APK вы собираете как сейчас.

## 9. Публикация веб-версии: постоянный адрес (реализовано в 0.9.55)

**Требование владельца (02.10.2026):** «независимо от количества новых веток
или переноса всего в основную ветку — никаких дополнительных ссылок,
переустановок и прочего быть не должно». Поэтому выбран вариант, где адрес
веб-версии **один и навсегда**:

```
https://help-yourself-dvp.github.io/LifeFlow-Fitness/
```

**Как это устроено.** Отдельный workflow **`pages.yml`** (зеркало
`tools/github-workflows/pages.yml`) при **каждом пуше в любую ветку** собирает
веб-папку (те же файлы, что едут в APK: `index.html`, `style.css`, `app.js`,
`sqlite-bundle.js`, шрифты, плюс `manifest.json`, `sw.js`, `version.txt`,
иконки) и складывает её в служебную ветку **`gh-pages`**. GitHub Pages
публикует `gh-pages` по адресу выше.

**Почему это закрывает требование владельца:**

- новая рабочая ветка (новый диалог) — адрес тот же, значок на «Домой»
  переустанавливать не нужно;
- перенос в `main` на финале проекта — адрес тот же, ничего перенастраивать
  не нужно: следующий же пуш снова обновит `gh-pages`;
- обновления доезжают сами: веб-версия сравнивает `version.txt` с
  установленной версией, при выходе новой — обновляет сохранённые файлы и
  один раз перезагружается;
- доступ к содержимому идёт по стандартному праву `contents: write`, которое у
  агента **уже есть**. Поэтому не нужен отдельный доступ GitHub Pages
  (`pages: write`), который пришлось бы одобрять владельцу и который «сломался
  бы» после слияния в `main`.

**Разовая настройка владельца (10 минут, один раз):**

1. Добавить файл workflow в рабочую ветку (две ссылки — в ответе агента:
   raw для копирования и `/edit/` для вставки), сделать commit.
2. Дождаться сборки **Publish Web (PWA)** во вкладке Actions — она создаст
   ветку `gh-pages`.
3. **Settings → Pages → Source: «Deploy from a branch» → Branch: `gh-pages`,
   папка `/ (root)` → Save.**
4. Открыть адрес в Safari → «Поделиться» → «На экран „Домой“».

Это единственный ручной шаг: файлы в `.github/workflows/` агент пушить не
может (нет прав), как когда-то с `build.yml`. После него всё работает без
участия владельца.

**Отвергнутые варианты:** Pages напрямую из рабочей ветки (замерзал бы при
каждой новой сессии — против требования «без ручных переключений»);
официальный деплой через среду `github-pages` (нужен отдельный доступ
`pages: write`, который владельцу пришлось бы одобрять; не проверяется из
песочницы)

## 12. Публичный репозиторий и «а если приложением начнут пользоваться другие»

Вопрос владельца (02.10.2026): «не смешаются ли наши данные с чужими и не
сломается ли что-то, если приложение сделают массово доступным».

**Смешаться не может — по устройству приложения.** У FitFlow нет сервера и нет
общей базы: все данные лежат в хранилище устройства (localStorage + SQLite в
IndexedDB) внутри конкретного origin/приложения. GitHub Pages отдаёт только
файлы кода. Поэтому:

- у каждого человека — свой независимый набор данных, даже если все открывают
  один и тот же адрес;
- два разных браузера на одном телефоне — тоже два независимых набора
  (на iPhone: вкладка Safari и значок «на Домой» — разные хранилища, § 3.3);
- наши данные нигде не публикуются: в репозитории лежат только код, иконки и
  документация.

**Что действительно меняется при массовом использовании** (честно, по пунктам):

1. **Трафик GitHub Pages.** Ограничения GitHub мягкие (порядка 100 ГБ в месяц):
   первая загрузка веб-версии — примерно 2,5 МБ со шрифтами, дальше всё из
   локального кэша. Это тысячи запусков в день до появления любых вопросов.
2. **Open Food Facts** (сканирование штрих-кодов). Лимит считается по IP
   пользователя, а не наш, и приложение кэширует ответы на устройстве и
   представляется (`app_name`/`app_version`). Для «своих» это не проблема.
3. **Облачный ИИ.** У каждого пользователя свой ключ и свои лимиты; в коде
   никаких наших ключей нет — ломаться нечему.
4. **APK и подпись.** Подпись одна (debug keystore в секрете репозитория), так
   что обновления ставятся поверх. Если кто-то пересоберёт APK со своим ключом,
   это не затронет уже установленное приложение: Android не позволит установить
   APK с другой подписью поверх (и наоборот).
5. **Рост числа обращений** — не техническая, а человеческая нагрузка:
   багрепорты и вопросы. Стоит решить заранее, куда их собирать.
6. **Единственное место, где массовость меняет архитектуру, — ФОНОВЫЕ
   НАПОМИНАНИЯ (P8).** Планировщик, который рассылает push, хранит адреса
   доставки (не данные, но факт устройства). Для себя — нормально; «для всех» —
   это уже маленький сервис, и тогда правильнее, чтобы у каждого пользователя
   был свой планировщик (как у каждого — свой приватный репозиторий в P5).
7. **Лицензия и дисклеймер.** Сейчас LICENSE — «личное использование,
   изменения без распространения»; при массовом распространении стоит решить,
   менять ли лицензию. Обязательное окно условий при первом запуске (данные
   справочные, не заменяют врача) уже есть и работает и в веб-версии.

**Вывод:** сегодня ничего делать не нужно — публичность безопасна для данных.
Когда/если приложение станет массовым, единственный обязательный разговор —
о планировщике напоминаний (P8) и о лицензии; всё остальное — организационное.
