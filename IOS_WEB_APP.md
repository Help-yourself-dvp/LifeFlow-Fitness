**Дата разбора:** 02.10.2026 · **Версия кода на момент разбора:** 0.9.54
**Статус:** план; решения владельца — в конце документа (§ 10).
**Тип документа:** проектный разбор по запросу владельца. Дополняет
`ROADMAP.md` (раздел «План по разработке под iOS») и `POSTPONED.md` (P26).

## 1. Короткий ответ на вопросы владельца

1. **Веб-версия делается не «с нуля».** FitFlow и так написан на чистых
   HTML/CSS/JS и уже открывается в браузере (см. README, «Как смотреть
   приложение в браузере»). Задача — не переписать приложение, а «докрутить»
   его до устанавливаемого приложения: манифест, служебный кэш (service
   worker), иконки, публикация по HTTPS. Это и есть PWA.
2. **Отдельный репозиторий для веб-версии не нужен.** Один код — две
   доставки: одни и те же файлы (`index.html`, `style.css`, `app.js`,
   `sqlite-bundle.js`, `assets/`) идут и в APK (Capacitor), и на сайт
   (GitHub Pages). Правите код один раз в одном месте.
3. **Правки, полезные iPhone, появляются на iPhone сразу** — после
   обновления страницы/перезапуска иконки на «Домой». Для Android всё как вы
   привыкли: новая сборка APK в GitHub Actions и установка поверх старой.
4. **Ядро сохраняется полностью:** вода, питание, парсер 960+ продуктов,
   «Комбо», «Мои блюда», «Мои продукты», статистика, силовой дневник,
   тренировки, вес, самочувствие, медали, профили, темы, экспорт/импорт
   копии файлом. **Теряются** те вещи, которые опираются на нативные API
   Android: фоновые напоминания, автоматические шаги/сон с часов, виджет
   рабочего стола, локальная нейросеть Gemma, кнопка на часах Wear OS
   (подробно — § 4, обходы — § 5).
5. **Синхронизация между устройствами реальна** и без «недоступных в РФ»
   сервисов. Ваш вариант — приватный репозиторий GitHub как хранилище
   файлов — рабочий; рядом есть Яндекс.Диск и совсем «без сервисов» —
   файл/AirDrop (§ 6). Это шаг 2, после работающей веб-версии.

## 3. Как это будет выглядеть в работе

### 3.1. Один раз на iPhone

1. Открыть адрес веб-версии в **Safari**.
2. Кнопка «Поделиться» → **«На экран „Домой“»** → «Добавить».
3. Дальше запускать **только с иконки на «Домой»**, а не из вкладки Safari —
   это важно (§ 3.3).

Никаких Apple ID, аккаунтов, TestFlight и 99 $/год. Приложение работает
офлайн (файлы кэшируются), данные лежат на телефоне.

### 3.2. Дальше — как обычное приложение

- Иконка на «Домой», открывается полноэкранно, без адресной строки.
- Вода/еда/тренировки/статистика — как на Android, интерфейс тот же.
- Копия файлом — «Настройки → Экспорт»: файл уходит в «Файлы → Загрузки»,
  оттуда его можно отправить себе в мессенджер/AirDrop.
- Обновление веб-версии — само (взял свежие файлы из сети при запуске),
  новая иконка не нужна. APK обновляется как сейчас.

### 3.3. Три особенности iOS, о которых надо знать заранее

1. **Установленное веб-приложение и Safari — разные хранилища.**
   Данные вкладки Safari не видны приложению с «Домой» и наоборот. Порядок
   такой: сначала установили на «Домой», потом начали вводить данные. Если
   начали в Safari — выгрузите копию файлом и импортируйте её уже в
   установленном приложении.
2. **Очистка хранилища.** Safari стирает данные сайтов, которые 7 дней не
   открывали. **На установленные веб-приложения это правило не действует** —
   у них свой счётчик и своя квота. Но привычка «копия файлом раз в месяц»
   всё равно остаётся правильной: удаление иконки или «Очистить историю и
   данные сайтов» данные уносят.
3. **Фон на iOS не работает.** Как только приложение ушло с экрана, iOS его
   приостанавливает: ничего не обновляется, ничего не «звонит» по таймеру.
   Поэтому на iPhone нет фоновой синхронизации и фоновых напоминаний —
   только при открытии (это уже учтено в логике приложения: сброс дня при
   возврате из фона, 0.9.53).

## 4. Что на iPhone в веб-версии не получится в принципе

Это не «мы не умеем», это ограничения iOS для сайтов и веб-приложений.
Честно и по пунктам:

1. **Виджет рабочего стола.** Safari-приложение не может добавить виджет на
   домашний экран iOS. Только нативное приложение (отдельная сборка под
   Apple и платная подписка разработчика). Обхода нет.
2. **Автоматические шаги и сон с часов/телефона.** Apple Health (HealthKit)
   закрыт для сайтов: веб-страница не имеет доступа к шагам, сну,
   тренировкам, весу. Обход — только через приложение «Команды» (§ 5.1).
3. **Напоминания при закрытом приложении.** У iOS-веб-приложений нет
   локальных уведомлений по расписанию. Push-уведомления технически есть
   (iOS 16.4+), но **требуют постоянного сервера-отправителя** — это ломает
   принцип «никаких серверов» и наших данных нигде. Обход — календарь и
   «Команды» (§ 5.2).
4. **Работа в фоне.** Никакого обновления в полночь, никакой фоновой
   синхронизации, никаких «тихих» напоминаний. Данные всегда актуальны на
   момент открытия приложения.
5. **Нейросеть Gemma на устройстве.** Это нативный Android-плагин
   (`plugins/fitflow-local-ai`, LiteRT-LM). На iOS он не собирается, а в
   веб-версии движка нет вовсе. Остаётся облачный ИИ по вашему ключу — и
   только если провайдер доступен из браузера.
6. **Кнопки на часах.** Аналога «+ 250 мл» с Wear OS для Apple Watch у
   веб-приложения нет.
7. **«Поделиться в FitFlow» из других приложений.** iOS не умеет отправлять
   данные из сторонних приложений в веб-приложение. Копировать текст
   придётся вручную (вставить в поле ввода еды).

Что при этом **остаётся полностью рабочим** (проверено по коду): вся вода и
питание, парсер фраз, «Комбо», «Мои блюда/продукты», журнал распознаваний,
статистика и сравнение периодов, активность (ручной ввод), силовой дневник
с шаблонами и таймером отдыха, вес, самочувствие, медали, профили, темы,
экспорт/импорт, онлайн-индикатор, чтение базы Open Food Facts для сканера.

## 5. Обходы без сторонних сервисов (всё внутри iPhone)

### 5.1. Шаги/сон/вес из Apple Health — приложением «Команды» (Shortcuts)

«Команды» умеют читать образцы Health (шаги, сон, тренировки, вес) и делать
HTTP-запрос. Дальше два пути:

- **С синхронизацией (шаг 2):** персональная автоматизация «в 23:00» читает
  шаги за день и кладёт их в то же хранилище, что и синхронизация
  (приватный репозиторий). Приложение подхватывает их при следующем
  открытии. Это ближайший аналог Health Connect, без нашего сервера.
- **Без синхронизации:** команда сохраняет число в «Файлы», вы раз в день
  открываете приложение и импортируете файл. Ручная работа — как вариант
  «на попробовать».

Честная оценка: полноценного автоматического шагомера, как на Android, у
веб-версии не будет. Это самый крупный функциональный минус веб-версии.

### 5.2. Напоминания — календарь или «Команды»

- **Календарь (`.ics`).** Приложение может выгрузить файл с событиями и
  сигналами (вода каждые 2 часа, приём курса по расписанию). Один раз
  импортировали в «Календарь» — напоминания работают системно, офлайн, без
  серверов. Минус: при изменении расписания файл надо импортировать заново
  (можно завести отдельный календарь «FitFlow» и очищать его целиком).
- **«Команды».** Автоматизация «в 21:00 → показать уведомление „Запиши воду
  в FitFlow“». Работает локально, настраивается один раз на телефоне.

### 5.3. Синхронизация между устройствами

См. § 6 — это и есть «шаг 2» из вашего запроса.

## 6. Синхронизация между устройствами (шаг 2)

### 6.1. Чего мы не используем и почему

- **iCloud/Firebase/Supabase/Google Drive** — аккаунты, лимиты, часть
  недоступна из РФ, а данные уходят третьей стороне. Не наш путь.
- **Свой сервер** — противоречит принципу «нет серверов, нет подписки».
- **WebRTC напрямую между телефонами** — технически возможно, но требует
  ручного «рукопожатия» и работает только когда оба устройства открыты.
  Хрупко, не для ежедневного трекера.

### 6.2. Вариант A (рекомендуемый): приватный репозиторий GitHub как хранилище

Ваша идея рабочая. Как это устроено правильно:

1. **Отдельный ПРИВАТНЫЙ репозиторий только для данных.** Не этот: наш
   репозиторий с кодом публичный, данные туда попасть не должны.
2. **Ключ (fine-grained token)** — только к этому приватному репозиторию,
   права «Contents: Read and write», срок — «без истечения». Ключ хранится
   **только на устройстве** (в данных приложения), в код и в публичный
   репозиторий не попадает. В приложении — поле ввода ключа и кнопка
   «Проверить связь»; отозвать доступ можно одной кнопкой на GitHub.
3. **Файлы по устройству, а не один общий.** Каждое устройство пишет свой
   файл: `devices/iphone-<id>.json`, `devices/android-<id>.json`. Так
   **конфликтов не бывает по построению** — устройства никогда не пишут в
   один файл. При чтении приложение сливает все файлы в один профиль.
4. **Слияние по времени.** Для записей хранится время изменения; старое
   проигрывает новому. Если правки были на двух устройствах в разные дни —
   обе сохраняются, ни одна не «затирает» другую.
5. **Когда синхронизируется:** при открытии приложения, после сохранения
   (с задержкой) и по кнопке «Синхронизировать сейчас». Фоново — нельзя
   (iOS), поэтому при закрытом приложении данные не уезжают, но и не теряются.
6. **Плюсы:** бесплатно, без серверов, GitHub вы уже используете; история
   версий файлов сама является архивом копий. **Минусы:** ключ лежит на
   телефоне (защищён паролем/биометрией телефона и ограничен одним
   приватным репозиторием); GitHub должен быть доступен — как и сейчас для
   скачивания APK.
7. **Бонус:** тот же формат синхронизации смогут использовать APK на
   Android — телефон и iPhone начнут видеть одни и те же данные.

### 6.3. Вариант B: Яндекс.Диск (если хочется «российское и стабильное»)

REST API + OAuth, папка приложения на Диске. Работает из РФ без VPN, у вас
уже есть аккаунт. Минус: нужно зарегистрировать приложение (10 минут) и
проверить, что запросы идут из браузера (CORS) — проверяется на практике.
Схема та же: файлы по устройству + слияние.

### 6.4. Вариант C: совсем без сервисов

Копия файлом + AirDrop/мессенджер между устройствами, импорт вручную.
Плюс: ноль настройки. Минус: руками, легко забыть.

**Рекомендация:** начать с A (GitHub), потому что он не добавляет ничего
нового в вашу жизнь — это тот же GitHub, только второй, приватный
репозиторий. Если что-то не устроит — B меняется почти без переделки логики
слияния.

## 7. Один репозиторий или два? Как вносить изменения?

**Код — один репозиторий** (`LifeFlow-Fitness`), как сейчас.

- Веб-часть (`index.html`, `style.css`, `app.js`, `sqlite-bundle.js`,
  `assets/`) — общая для Android и iPhone. Изменили один раз — на iPhone
  прилетело сразу, на Android — после новой сборки APK.
- Android-натив (`android-native/*.java|kt`, `android-res/`, workflow) —
  живёт в том же репозитории, но на веб-версию не влияет вовсе.
- Добавлять «веб-специфичные» файлы (`manifest.json`, `sw.js`, иконки для
  iOS) будем аккуратно, чтобы сборка APK их не тянула (там Capacitor
  генерирует свои манифест и иконки).

**Второй репозиторий (приватный) появляется только на шаге синхронизации —
и это не репозиторий кода, а хранилище файлов данных.** Изменения
функционала в него вносить не нужно никогда: он просто «флешка в интернете».

Итог по вашему вопросу: **в несколько репозиториев код не разъезжается.**
Одна правка — одно место. Разная только «упаковка»: сайт обновляется сам,
APK вы собираете как сейчас.

## 9. Публикация веб-версии: где и с каким адресом

**GitHub Pages** — бесплатно, без аккаунтов, HTTPS (для камеры и офлайн-кэша
HTTPS обязателен). Репозиторий публичный, поэтому Pages доступен без
платного тарифа.

Адрес будет вида:
`https://help-yourself-dvp.github.io/LifeFlow-Fitness/`

Тонкость, которую надо решить (§ 10): GitHub Pages отдаёт файлы **из
выбранной ветки репозитория**, а у нас рабочая ветка меняется каждую сессию
(`arena/…`), и `main` сейчас — **старый снимок** (там нет даже
`sqlite-bundle.js`). Варианты:

- **Старт (рекомендую):** указать в настройках Pages текущую рабочую ветку.
  Обновления идут с каждого пуша, адрес не меняется. Когда начинается новая
  сессия и появляется новая ветка — переключить ветку в настройках Pages
  (30 секунд), иначе веб-версия «замерзает» на прежнем состоянии.
- **Зрелый вариант:** обновлять Pages из `main`, а `main` — периодически
  обновлять слиянием рабочей ветки. Это меняет старое правило «перенос в
  `main` — самый последний шаг»: для веб-версии выпуском становится слияние.
  Понадобится отдельная версия на первое большое слияние (там накопилась
  разница).
- **Автоматический вариант:** workflow сборки Pages (GitHub Actions). Тогда
  Pages всегда отражает последний пуш в любой ветке. Но файлы workflow агент
  пушить не может (нет прав) — файл придётся один раз создать вам через
  редактор GitHub, как когда-то с `build.yml`.

1. **Стартуем ли с шага P1** (каркас PWA + публикация + установка на iPhone)?

## 11. Риски и как их снимаем

| Риск | Что делаем |
|---|---|
| Safari «не умеет» какой-то API из наших | проверяем на живом iPhone; всё, что не работает, **скрываем**, а не оставляем «мёртвую» кнопку (правило «никаких заглушек») |
| Потеря данных на iPhone | привычка копии файлом + предупреждение в интерфейсе + шаг P5 (синхронизация = ещё и бэкап) |
| Веб-версия отстала от APK по версии | одна версия кода на оба канала; на iPhone в «О приложении» будет виден актуальный номер версии и сборки |
| Ключ синхронизации утёк | fine-grained token только к одному приватному репозиторию, хранение только на устройстве, отзыв в один клик, ключ не попадает в копии и логи |
| Расхождение Android- и веб-веток поведения | обе ветки опираются на общий веб-слой; нативный код не «зашивается» в бизнес-логику (уже так) |

## 12. Ответ одной строкой

Да, это делается; отдельный репозиторий не нужен; ядро приложения
сохраняется целиком; потеряются виджет, фоновые напоминания и автоматический
шагомер — их закрываем календарём/«Командами» и синхронизацией; Android
продолжает жить как сейчас — новый APK поверх старого.
