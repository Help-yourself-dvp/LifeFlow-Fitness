- `EXTRA_SPEECH_INPUT_COMPLETE_SILENCE_LENGTH_MILLIS` /

- `EXTRA_PARTIAL_RESULTS` — потоковые частичные результаты (видно текст
  на ходу, понятно, что слышит распознаватель).
Своя модель распознавания (Vosk и т.п.) НЕ рассматривается: вес и сложность

## P7. Штрих-код: полная офлайн-база и сканер камерой

**Цель:** сканировать штрих-код с упаковки камерой и получать точные
калории/БЖУ именно этого продукта (приоритет правдивости).

**Что НЕ работает (проверено проектированием 0.3.27):**
- **Полная офлайн-база штрих-кодов в APK** — нереализуема честно: Open Food
  Facts держит миллионы позиций (гигабайты), пополняется ежедневно, а RU-
  покрытие неполное даже онлайн. Паковать устаревающий срез = ввести
  пользователя в заблуждение. Так НЕ делает ни один аналог: FatSecret/
  YAZIO ходят в свои облачные базы, MFP — крауд.
- **Своя закрытая RU-база** — платная лицензионная работа, не наш масштаб.

**Что сделано (0.3.27):** ручной ввод штрих-кода → онлайн OFF API →
подстановка в форму «Мои продукты» → офлайн навсегда (личная база = честный
кэш с бэкапом). Атрибуция ODbL на месте.

**Путь сканера камерой (ждёт решения пользователя), нативно — build.yml:**
1) `uses-permission android.permission.CAMERA` (+ uses-feature camera,
   required=false);
2) в MainActivity `WebChromeClient.onPermissionRequest` → `request.grant(...)`
   для RESOURCE_VIDEO_CAPTURE (иначе getUserMedia в WebView молчит);
3) сканер: ZXing-browser (файл ~0.5 МБ в APK, офлайн) или нативный ML Kit
   (градл-зависимость, точнее, но тянет Google Maven).
Связать: отсканированный код → готовый lookupOffByBarcode() → форма.

## P1. Поля Питания и «Своя мл» — панель с кнопками над клавиатурой

**Цель:** при открытой клавиатуре поле и его кнопки («Добавить», «✓») должны
быть видны над ней, чтобы не скрывать клавиатуру для отправки.

**Провалившиеся подходы:**
- **Мгновенный IME-док** (0.3.18, build 136): перенос контейнера в
  fixed-панель в тик `focusin`. Результат: подъём клавиатуры гасится,
  нужен второй тап. Причина: IME-запрос Chromium инициируется после focusin,
  перенос ноды в этот момент его обрывает.
- **Отложенный IME-док** (0.3.19, build 137): перенос по факту просадки
  visualViewport (клавиатура открыта). Результат: клавиатура открывается и
  сразу прячется; в «Своей мл» поле «уезжает» спустя секунду. Причина:
  перенос ноды при активной IME-сессии её рвёт (фокус сохраняется,
  IME-сессия — нет).

**Вывод (0.3.20):** ноды пользовательских полей НЕ двигаем — никогда.
Возвращено стабильное поведение: поле на месте, `adjustResize` сам
докручивает его в видимую зону. Авто-док оставлен только для полей ИИ
(там фокус программный — «сжигатель мёртвой первой IME-сессии»), и во всех
текстовых вкладках ИИ это подтверждённо удобно.

**Активная проба (0.3.21):** `scrollIntoView` по факту просадки viewport
(без переноса ноды, один раз за сессию фокуса, для `#food-input` и
`#water-custom-ml`). **Вердикт пользователя (07.08, build 139): «отлично» —
проба принята.** Часть цели «не скрывать клавиатуру для отправки» остаётся
открытой мягко (кнопка «Добавить» прямо под полем); окончательная «панель
над клавиатурой» без переноса ноды — только нативным путём, отложено за
основной функционал.

## P2. Программный подъём клавиатуры при открытии ИИ-центра

**Цель:** вход в ИИ → клавиатура уже поднята (тап меньше).

**Провалившиеся подходы:**
- **blur/focus-ретрай через 450 мс** (0.3.18, build 135–136): неэффективен —
  Chromium принципиально не показывает клавиатуру по программному фокусу
  без пользовательского жеста над полем. Код удалён.
- **requestFocus-прогрев WebView нативно** (патч build.yml, build 135):
  симптом не снял (нужен именно жест пользователя).

**Что достигнуто вместо:** автофокус поля в пользовательском жесте «сжигает»
мёртвую первую IME-сессию → реальный тап пользователя уже работает
(клавиатура + голос с первого раза, build 136 подтверждён). Пользователь
принял такой сценарий как устроивающий. Финальный подъём появится только с
нативным вызовом `InputMethodManager.showSoftInput` по таймеру после
открытия экрана — отдельным нативным патчем (не планируется, сценарий устраивает).

в ИИ после холодного старта.

**Провалившиеся подходы (каждый — отдельный релиз, симптом битово идентичен):**

холодного старта обречена, вторая+ — живые; автофокус «сжигает» первую —

## P5. Порционные дефолты вместо «100 г по умолчанию»

**Цель:** меньше «≈100 г» там, где бытовая порция очевидно другая.

**Что уже сделано:** штучные продукты — `per: 'шт'` с точным ккал/шт
(сосиска, бутерброд, глазированный сырок…); хлебное семейство — веса долей
(кусок 40 г / ломтик 30 г, 0.3.19); ёмкости — `UNIT_MAP` (стакан 250 мл,
тарелка 200 г……). Честный принцип: без веса → ≈100 г и эта оценка всегда
видна пользователю.

**Отложено:** порционные дефолты по КАТЕГОРИЯМ (тарелка супа 250–300 мл,
порция гарнира 180–200 г…) — требует курируемой таблицы и согласования;
риск «молчаливого завышения» важнее, чем удобство.
**Снимет проблему системно:** сценарий «Фото еды» (ИИ оценивает вес по
снимку) — дорожная карта.
