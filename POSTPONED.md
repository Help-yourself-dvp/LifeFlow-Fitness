## P1. Поля Питания и «Своя мл» — панель с кнопками над клавиатурой

**Цель:** при открытой клавиатуре поле и его кнопки («Добавить», «✓») должны
быть видны над ней, чтобы не скрывать клавиатуру для отправки.

**Провалившиеся подходы:**
- **Мгновенный IME-док** (0.3.18, build 136): перенос контейнера в
  fixed-панель в тик `focusin`. Результат: подъём клавиатуры гасится,
  нужен второй тап. Причина: IME-запрос Chromium инициируется после focusin,
  перенос ноды в этот момент его обрывает.
- **Отложенный IME-док** (0.3.19, build 137): перенос по факту просадки
  visualViewport (клавиатура открыта). Результат: клавиатура открывается и
  сразу прячется; в «Своей мл» поле «уезжает» спустя секунду. Причина:
  перенос ноды при активной IME-сессии её рвёт (фокус сохраняется,
  IME-сессия — нет).

**Вывод (0.3.20):** ноды пользовательских полей НЕ двигаем — никогда.
Возвращено стабильное поведение: поле на месте, `adjustResize` сам
докручивает его в видимую зону. Авто-док оставлен только для полей ИИ
(там фокус программный — «сжигатель мёртвой первой IME-сессии»), и во всех
текстовых вкладках ИИ это подтверждённо удобно.

**Активная проба (0.3.21):** `scrollIntoView` по факту просадки viewport
(без переноса ноды, один раз за сессию фокуса, для `#food-input` и
`#water-custom-ml`). **Вердикт пользователя (07.08, build 139): «отлично» —
проба принята.** Часть цели «не скрывать клавиатуру для отправки» остаётся
открытой мягко (кнопка «Добавить» прямо под полем); окончательная «панель
над клавиатурой» без переноса ноды — только нативным путём, отложено за
основной функционал.

**Статус (12.08.2026):** интеграция начата в сессии 0.7.6, нативная сборка НЕ прошла.

Нативная часть (реальное чтение из Health Connect API) — в доработке.

### Что пробовали и не получилось (сессия 12.08.2026):

**Итерация 1 — `connect-client:1.1.0-alpha11` + `compileSdk 35`:**
- Ошибка: `connect-client:1.1.0-alpha11` требует `compileSdkVersion ≥ 35`.
- Подняли compileSdk до 35 → `android-35/android.jar` не установлен в CI-окружении
  GitHub Actions (AGP 8.0.0 Capacitor тестирует до compileSdk 33).
- Установка SDK platform-35 в CI не решает проблему: `aapt2` из AGP 8.0.0 не
  умеет читать ресурсы platform-35.

**Итерация 2 — `connect-client:1.0.0-alpha12` + `compileSdk 34`:**
- Ошибка: версия `1.0.0-alpha12` **не существует** в Maven. Серия 1.0.x
  заканчивается на `alpha11` (февраль 2023).

**Итерация 3 — `connect-client:1.0.0-alpha11` + `compileSdk 34` + Java ListenableFuture:**
- Ошибка: `com.google.common.util.concurrent` (Guava: Futures, FutureCallback,
  ListenableFuture) **не подключается** как транзитивная зависимость connect-client.
- Дополнительно: `ReadRecordsRequest` в 1.0.x принимает `KClass` (Kotlin), а не
  `Class` (Java); `readRecords()` — suspend-функция, нельзя вызвать напрямую из Java.

**Итерация 4 — `connect-client:1.0.0-alpha11` + Kotlin-хелпер + `runBlocking`:**
- Создан `HealthConnectHelper.kt` с `@JvmStatic fun syncNow()` через `runBlocking`.
- Добавлена зависимость `kotlinx-coroutines-android:1.7.3`.
- Ошибка: `sed`-команда для добавления coroutines-зависимости в Gradle была
  с неправильным экранированием (лишние слэши + лишний `' android/app/build.gradle`).
- **Статус: sed исправлен, зеркало обновлено, ждёт замены workflow пользователем.**

### Корневая проблема:

Capacitor 5.7.0 использует AGP 8.0.0 + Gradle 8.0.2, которые тестируются до
compileSdk 33. Любая библиотека, требующая compileSdk 34+, рискует сломать
сборку. Health Connect `connect-client` серии 1.0.x (до alpha11) совместим с
compileSdk 34, но написан на Kotlin с suspend-функциями — вызов из Java требует
`kotlinx-coroutines` + `runBlocking` в отдельном .kt файле.

**Дополнение (0.5.4, уточнение владельца):** источников шагов может быть ДВА
одновременно — телефон и браслет/часы. Правило приоритета без двойного счёта:

**Кейс пользователя (0.4.14):** конкурент «Худеем вместе» синхронизируется с

**Цель:** читать из Health Connect шаги, активные минуты и сон за сегодня и

эксперт). Запись в Health Connect не требуется (пишет часы/другие приложения).

**План реализации:**
1. Gradle: зависимость `androidx.health.connect:connect-client` (в шаблон

2. Манифест: разрешения `android.permission.health.READ_STEPS`,

   `queries`-блок пакета Health Connect; activity-alias для экрана

3. Нативный мост (по образцу FitFlowExport/FitFlowLocalAI): методы

   `hasPermissions()`, `requestPermissions()` (ActivityResult-контракт),

4. JS: Настройки → новый блок «Данные с часов» (статус, кнопка подключения,
   что читаем); в Статистику — шаги/активность из HC с пометкой источника;
   в gatherProgressFacts — sleep/steps из HC как дополнительный слой поверх

5. Тесты: node-проверка нормализации HC-пакета (как normalizeDailyHistory);

**Честные ограничения:** Health Connect есть не на всех прошивках (ожидается
Android 14+ или отдельное приложение на 13-), данные зависят от того, что
пишет производитель часов; ничего не выдумываем — при отсутствии HC блок
прячется за статусом «не поддерживается на этом устройстве».

**Почему не сейчас:** правки build.gradle/манифеста встроены в build.yml
heredoc'ами — любая нативная правка требует ручной замены workflow
пользователем; драйвить её отдельным релизом, не смешивая с JS-фичами 0.4.14.

### P26. FitFlow на iPhone: PWA как пробный формат, SideStore как расширенный путь

Вопрос владельца (10.08.2026): «Для iPhone PWA — реальный обход App Store

  рабочая схема; для распространения — нет (каждому пользователю — свой обряд).
- Аккуратно сказано владельцу: iOS-этап существует как исследование; команда

### P31. Двойной учёт калорий: шаги + тренировки (бег) — ✅ РЕШЕНО (0.8.2)
**Кейс (13.08.2026, зафиксировано владельцем «очень важно, не потерять»):** в
«балансе питания» сожжённые калории считались как `тренировки (MET) + шаги × 0,04` —
при беге шаги учитывались бы дважды (в шагах и в MET-оценке). Заодно вскрылось, что
`workout.kcal` не сохранялся → калории тренировок фактически НЕ добавлялись вовсе.
**Решение (0.8.2):** `computeFoodBudgetAdjustmentPure(workouts, steps, weightKg)`:
`тренировки (MET) + шаги × 0,04 − пересечение`, где пересечение = шаги за время
«шагающих» тренировок (бег 160 / ходьба 120 шагов/мин), ограничено `≤ stepsKcal`.
MET для силовой/велосипеда/плавания не создаёт пересечения (0 шагов). Покрыто
node-регрессом; разбор виден в подсказке цели питания и в статусе карточки.

### P33. ИИ-рекомендации по тренировкам (не навязчиво)
**Цель (идея владельца, 13.08.2026):** приложение делает многое само — смотрит прогресс
(растёт ли 1RM), перерывы между силовыми, равномерность нагрузки по группам — и выдаёт
1–2 коротких совета («жим лёжа не растёт 3 недели — попробуйте +1 повтор вместо +2.5 кг»,
«ноги без нагрузки 6 дней — добавьте присед»). **Не навязчиво:** никаких пушей/плашек —
советы живут в «Прогрессе силовых» и в анализе, по явному открытию.
**Почему не сейчас:** сначала — детерминированные правила (чистый JS, без ИИ); ИИ-текст —
опциональный слой поверх фактов (встроенный анализ / нейросеть на устройстве). Делается
отдельной небольшой версией после стабилизации дневника силовых (0.8.x) и P28.
