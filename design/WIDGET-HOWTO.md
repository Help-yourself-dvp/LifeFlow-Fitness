# Как создаётся виджет FitFlow

Рабочая инструкция: что и в каком порядке трогать, чтобы сделать **новый**
виджет или переделать существующий, не изучая проект заново. Написана по
итогам бенто 0.9.24 → 0.9.28, где одни и те же грабли ловились полем
четыре версии подряд.

Смежные документы: `design/WIDGET-P5.md` (что виджет в принципе умеет и чего
не умеет — потолок RemoteViews), `SESSION_HANDOFF.md` (протокол работы),
`PROJECT.md` # 2.9 (карта контуров).

---

## 0. Правило номер один

**Виджет рисует не приложение, а лаунчер** — по описанию `RemoteViews`.
У нас нет своей View, нет Canvas на рабочем столе, нет доступа к обоям.
Поэтому всё, что виджет умеет, — это готовая иерархия из ограниченного
набора вьюх и заранее подготовленные картинки.

Из этого следует практический вывод, который стоил четырёх версий:

> Всё, что должно **совпадать** с живыми данными, обязано лежать в
> **одной системе координат**. Нельзя часть рисовать в картинке, а часть —
> в разметке, и надеяться, что они сойдутся.

Именно так в 0.9.27 кроссовок «наступал» на кольцо: кроссовок был в PNG
(растягивается `fitXY` вместе со всей картинкой), кольцо — в dp-разметке.
На каждом размере ячейки они расходились по-разному.

## 1. Две архитектуры виджета, и когда какую брать

### A. Canvas-виджет (`FitFlowWidgetDropProvider`, `...NeonProvider`)

Натив рисует **весь** кадр в `Bitmap` через `FitFlowWidgetPaint` и отдаёт
одной картинкой (`setImageViewBitmap`), кнопки — прозрачный оверлей сверху.

- ➕ любая графика: волны, свечение, произвольные дуги;
- ➖ текст в bitmap не масштабируется системным шрифтом, не читается
  скринридером, при смене размера ячейки надо перерисовывать всё.

Берём, когда виджет **декоративный** и цифр мало.

### B. Подложка + overlay (`FitFlowWidgetBentoProvider`) — рекомендуемая

Статичная PNG-подложка (только геометрия: оболочка и плиты) плюс живые
`TextView` / `ProgressBar` / `ImageView` поверх.

- ➕ текст остаётся текстом (шрифт системы, доступность, `ellipsize`);
- ➕ показатели меняются без перерисовки картинки;
- ➖ подложка и overlay обязаны жить в одной сетке (см. § 3).

**Для нового виджета по умолчанию берите B.**

## 2. Какие файлы участвуют

| Файл | Роль |
|---|---|
| `tools/prepare-<имя>-bg.py` | готовит подложку и иконки в `design/` |
| `design/widget_<имя>_bg_round.png` | подложка (в APK → `drawable/`) |
| `design/widget_<имя>_ic_*.png` | иконки слотов |
| `android-res/layout/fitflow_widget_<имя>.xml` | разметка overlay |
| `android-res/drawable/*.xml` | шкалы, кольца, кнопки (shape/layer-list) |
| `android-native/FitFlowWidget<Имя>Provider.java` | данные, слоты, клики |
| `android-native/FitFlowWidgetData.java` | **общий** источник цифр |
| `.github/workflows/build.yml` + зеркало | копирование ресурсов, `*_info.xml`, регистрация в манифесте |
| `test-ui-init.js` | сторож инвариантов |

Каталог `android-res/` копируется в APK целиком (шаг «Patch manifest and
icons»), PNG из `design/` — поимённо. **Забыли добавить PNG в список
копирования — в APK его не будет, а виджет молча останется без иконки.**

## 3. Сетка: единственный способ совместить картинку и overlay

Подложка растягивается `android:scaleType="fitXY"` — то есть **в процентах**
от размера ячейки. Значит, overlay тоже должен быть в процентах:
`layout_weight` + `weightSum`, никаких фиксированных dp для позиций плит.

Рецепт:

1. В скрипте подложки задайте сетку числами и **запишите их в docstring**
   (у бенто: холст 1200×675, поле 36, промежуток 30, левая плита 538).
2. Переведите те же числа в веса: `36/1200 = 3 %` → `layout_weight="30"`
   при `weightSum="1000"`.
3. В шапке разметки повторите сетку комментарием и напишите, что
   менять её можно **только парой** со скриптом.

Фиксированные dp допустимы **внутри** плиты (отступы текста, диаметр
кнопки) — там они и нужны, чтобы кнопка не «поплыла» на крупной ячейке.

## 4. Бюджет высоты — считайте ДО вёрстки

Самая частая полевая ошибка: контент не влезает, и Android режет нижний
элемент. Именно так у бенто «обрезало нижнее закругление пилюли» — плита
получала 62 dp, а содержимому требовался 71 dp.

Считайте так:

```
высота плиты = minHeight ячейки × доля строки × доля плиты
нужно        = padding + подпись + значение + цель + зазор + шкала + padding
```

Бенто на 4×2 (`minHeight=150`), версия 0.9.28 — как считать **не надо**:

```
плита  150 × 0.882 × 0.472 = 62.4 dp
нужно  6+14.2+18.9+13+2+10+6 = 71.1 dp   → НЕ ВЛЕЗАЕТ
```

Тогда виджет подняли до 4×3 (180 dp), и это была ошибка проектирования,
а не арифметики. **Прежде чем просить у виджета высоту, отберите её у
воздуха.** В 0.9.30 тот же контент лёг в 4×2 без единого изменения кегля,
потому что нашлись четыре источника:

| Источник | Было | Стало | Выигрыш |
|---|---|---|---|
| круглая кнопка по центру плиты | делит высоту с текстом | угол `top\|end` | ~14 dp |
| размер кнопки | 46 dp | 38 dp | сам не даёт высоту, но освобождает ширину |
| поля подложки по вертикали | 36 px | 14 px | ~5 dp |
| промежуток между плитами | 30 px | 20 px | ~2 dp |
| кольцо в крупной плите | 104 dp | 72 dp | ~32 dp |

Итог 0.9.30 (`minHeight=150`, веса `26/948/26` и `480/40/480`):

```
плита  150 × 0.948 × 0.480 = 68.3 dp
нужно  4 + 13.9 + 1 + 19.7 + 12.8 + 15 = 66.4 dp   → влезает, запас 1.9 dp
       pad  label  gap value  goal   низ (шкала 10 + отступ 5)
```

Крупная плита, та же ячейка: `150 × 0.948 = 142.2 dp`; снизу 46 dp
занимает пара «значение + цель», сверху 22 dp — подпись; кольцо 72 dp со
сдвигом `marginBottom=26dp` ложится в 22.1…94.1 dp и ничего не задевает.

Порядок действий, когда не влезает:

1. **убрать воздух** — кнопки из центра в угол, поля подложки, промежутки,
   диаметр кольца (0.9.30: хватило только этого);
2. **дать виджету высоту** (4×2 → 4×3) — честно, но пользователь платит
   местом на экране, и попросит вернуть обратно;
3. убрать строку (например, показывать только «1 000 / 2 300»);
4. уменьшить кегль — **последнее средство**: ниже 11 sp текст на виджете
   уже нечитаем, и владелец прямо запретил этот путь.

Чего делать **нельзя** — оставить как есть в надежде «на большом экране
поместится». Ячейка 4×2 есть у всех.

И зеркальная проверка по **ширине**: строка «1 000 из 2 300 мл» рядом с
круглой кнопкой в одну строку не помещается (нужно 110 dp, есть 75) —
поэтому значение и цель разнесены на две строки во всех плитах.

Чтобы шкала не срезалась при любой ошибке в расчётах, кладите её
**отдельным слоем, прижатым к низу плиты**, а не последней строкой
текстовой колонки (0.9.30):

```xml
<!-- внутри FrameLayout плиты, ПОСЛЕ текстовой колонки -->
<FrameLayout android:layout_height="10dp" android:layout_gravity="bottom"
             android:layout_marginBottom="5dp"> <ProgressBar ... /> </FrameLayout>
```

А растягиваться пусть будет строка цели (`layout_height="0dp"`,
`layout_weight="1"`) — если лаунчер выдаст плиту ниже расчётной, лишнее
съест текст, а не полоса. Распорка `<View>` для этого **не годится** —
см. § 5, виджет вообще не добавится на экран.

## 5. Ограничения RemoteViews, о которые бьются регулярно

| Хочется | Реальность | Обход |
|---|---|---|
| сменить `progressDrawable` по данным | метода нет в белом списке | наложить по одной шкале на показатель и переключать `setViewVisibility` |
| поменять цвет текста по данным | только `setTextColor` (есть) | — |
| размыть обои под карточкой | API не существует | полупрозрачная карточка; blur даёт сам лаунчер (Samsung) |
| анимация | нет | статика; ripple по нажатию системный |
| произвольный шрифт | нет доступа к `assets` из RemoteViews | системные `sans-serif` семейства |

### Белый список вьюх — самая дорогая ошибка

Разрешены **только**: `FrameLayout`, `LinearLayout`, `RelativeLayout`,
`GridLayout`, `TextView`, `ImageView`, `ImageButton`, `Button`,
`ProgressBar`, `Chronometer`, `AnalogClock`, `ViewFlipper`, `ViewStub`,
`ListView` / `GridView` / `StackView` / `AdapterViewFlipper`
(последние — через `RemoteViewsService`).

**Обычный `<View>` в этот список НЕ входит.** И `<Space>` тоже.

Это ловушка, потому что `<View>` — первое, что приходит в голову для
распорки, и в обычной вёрстке он абсолютно нормален. Здесь же лаунчер не
может раздуть разметку, и виджет **не добавляется на экран вообще**:
пользователь видит чёрный прямоугольник и «Не удалось добавить виджет».

Ошибка «немая» с точки зрения разработки: проект собирается, APK ставится,
остальные виджеты работают, `aapt` не ругается — падает только инфляция у
лаунчера в рантайме. Поймали этим полем в 0.9.28 (восемь `<View>`-распорок).

**Вместо `<View>` — пустой `FrameLayout`:** ведёт себя точно так же
(прямоугольник с `layout_weight`), но разрешён.

```xml
<!-- НЕЛЬЗЯ: виджет не добавится -->
<View android:layout_width="match_parent" android:layout_height="0dp"
      android:layout_weight="1" />

<!-- МОЖНО -->
<FrameLayout android:layout_width="match_parent" android:layout_height="0dp"
             android:layout_weight="1" />
```

Кастомные классы, `merge`, `include`, `androidx.*` вьюхи, `app:`-атрибуты
и `android:onClick` — тоже нельзя. Клики только через
`setOnClickPendingIntent`.

Сторож — тест «0.9.29 … белого списка RemoteViews» в `test-ui-init.js`:
он сканирует и `android-res/layout/`, и разметки, которые генерирует CI.

## 6. Шрифты: одно правило

Всё, что видит пользователь, задаётся **в разметке**, одним семейством
`sans-serif`. Жирным — только значения и надпись на кнопке; подписи и
цели — `normal`.

Разнобой 0.9.27 («Шаги» тонким, «Вода» и «Калории» жирным) возник ровно
потому, что часть подписей была впечатана в картинку, а часть рисовал
TextView. **Не впечатывайте текст в подложку** — его нельзя ни
переименовать, ни согласовать по начертанию, ни перевести.

## 7. Настраиваемые слоты

Состав уже хранится в приложении: `state.widgetLayout.items` →
prefs `widgetItems` → `FitFlowWidgetData.items` / `d.shows(id)`.
Список пунктов — `WIDGET_ITEMS` в `app.js`.

Схема для нового виджета:

```java
private static final String[] SUPPORTED = { "steps", "water", "food", "activity" };

private static ArrayList<String> slotsFor(FitFlowWidgetData d) {
    ArrayList<String> out = new ArrayList<String>();
    for (String id : SUPPORTED) if (d.shows(id)) out.add(id);
    if (out.isEmpty()) { out.add("steps"); out.add("water"); out.add("food"); }
    return out;
}
```

Правила:

- в `SUPPORTED` — только показатели, которые виджет умеет нарисовать
  (у бенто это пары «значение / цель»; текстовой строке в плите со шкалой
  места нет);
- пустой слот **прячется целиком** (`View.GONE`), а не показывает нули —
  правило «никаких видимых заглушек»;
- пустое пересечение → разумный запасной набор, чтобы виджет не оказался
  пустым прямоугольником.

## 8. Кнопки

| Действие | Механика | Открывает приложение? |
|---|---|---|
| `ADD_WATER_250` | `getBroadcast` → `FitFlowWidgetProvider` | нет, пишет в prefs |
| `smart_entry` | `getActivity` → `MainActivity` + `putExtra("widget_action", …)` | да, «Быстрый ввод» |
| `ACTION_COURSE_DOSE` | `getBroadcast` | нет |
| `ACTION_REFRESH` | `getBroadcast` | нет |
| `widget_settings` | `getActivity` + `putExtra` | да, диалог состава виджета |

Обязательно `PendingIntent.FLAG_IMMUTABLE` (Android 12+) и **уникальный
requestCode** на каждую кнопку — иначе интенты перезапишут друг друга и
все кнопки станут делать одно и то же.

Почему еду нельзя записать одним тапом, как воду: у воды фиксированная
доза, у еды — блюдо и калории, их надо ввести. Поэтому карандаш честно
открывает экран ввода, а не «добавляет что-то».

**Где размещать кнопку (0.9.30).** Круглая кнопка по центру плиты
съедает всю её высоту: текст жмётся влево, под ним пустота, полоса
прогресса уезжает к нижней кромке. Ставьте кнопку в угол
(`layout_gravity="top|end"`) и давайте текстовой колонке `paddingEnd`
шириной кнопки плюс отступ — тогда полоса ложится во всю ширину плиты.
Размер: 38 dp — минимум, который ещё уверенно попадается пальцем;
46 dp на маленькой плите выглядит кнопкой-переростком.

**Яркость.** Кнопка действия не должна быть самым ярким пятном виджета.
Берите цвет показателя и приглушайте его на пару ступеней (питание:
`#FF8A5C` → `#D9714A`), иначе на тёмном рабочем столе она «выжигает» угол.

**Служебная кнопка** (шестерёнка настроек) — наоборот, максимально
незаметная: серый `#96A0B0`, `alpha=0.55`, 16 dp картинки внутри 26 dp
области нажатия. Ведите её не «в приложение вообще», а сразу в нужный
диалог: у бенто это `widget_settings` → `switchView('settings-general')`
→ `openWidgetLayoutDialog()`.

## 9. Регистрация в CI

В `.github/workflows/build.yml` (и **сразу** в зеркале
`tools/github-workflows/build.yml`):

1. копирование PNG из `design/` в `drawable/`;
2. запись `xml/fitflow_widget_<имя>_info.xml` (`minWidth`, `minHeight`,
   `targetCellWidth/Height`, `resizeMode`, `updatePeriodMillis="0"`);
3. регистрация `<receiver>` в манифесте — список `canvas_infos` /
   провайдеров.

Активный workflow и зеркало обязаны **совпадать побайтно**: первый шаг
сборки это проверяет и предупреждает. Владелец заменяет активный файл
вручную — без этого новый натив в APK не попадёт.

## 10. Как проверить без телефона

В песочнице нет Android SDK, поэтому:

1. **XML парсится**
   `python3 -c "import xml.dom.minidom as m; m.parse('android-res/layout/…')"`
2. **Все `R.id` из провайдера объявлены в разметке** — сверить регулярками
   (несуществующий id ловится только при сборке).
3. **Ни одной вьюхи вне белого списка** (§ 5) — иначе виджет не добавится
   на экран, а узнаете вы об этом только с телефона.
4. **Предпросмотр** `python3 tools/widget-bento-preview.py` — повторяет
   ту же сетку весов и рисует результат. Предпросмотр обязан **обрезать
   текст многоточием** так же, как Android, иначе он врёт в нашу пользу.
5. **Тесты** `node test-ui-init.js` — сторожат инварианты (см. § 11).
6. Арифметика бюджета высоты из § 4 — руками, до вёрстки.

---

## 11. Что закрепить тестом

Тест должен ловить не «файл существует», а **инварианты, поломка которых
уже случалась**:

- на подложке нет ни одного показателя (иначе слоты перестанут
  настраиваться, а иконка разъедется с кольцом);
- иконка и кольцо — в одном центрированном контейнере;
- ни одного `sans-serif-medium`, `bold` ровно у значений и кнопки;
- «значение / из цели» одинаково во всех плитах;
- состав слотов идёт из `d.shows(...)`, а не зашит;
- пустой слот скрывается;
- шкала прижата распоркой;
- высота ячейки соответствует расчёту;
- зеркало копирует все PNG.

## 12. Чек-лист нового виджета

1. Нарисовать сетку на бумаге, посчитать бюджет высоты (§ 4).
2. `tools/prepare-<имя>-bg.py` — подложка **только с геометрией** + иконки.
3. `android-res/layout/fitflow_widget_<имя>.xml` — overlay на весах (§ 3).
4. `android-res/drawable/` — шкалы, кольца, кнопки по одному на показатель.
5. `FitFlowWidget<Имя>Provider.java` — слоты, данные, клики (§ 7, § 8).
6. Обновить `updateAll` в общей точке (`FitFlowWidgetProvider`), чтобы
   виджет обновлялся вместе с остальными.
7. Прописать в оба workflow (§ 9).
8. Предпросмотр + тесты (§ 10, § 11).
9. Обновить `version.txt`, `app.js`, `index.html`, `CHANGELOG.md`,
   `APP_DESCRIPTION.md`.
10. В отчёте владельцу — что проверить в поле на телефоне.

## 13. Canvas-виджет: что выяснилось на «кольцах» (0.9.32)

Второй путь из § 1 — рисовать всё картинкой. Он снимает почти все
ограничения RemoteViews, но добавляет свои.

**Кнопки.** Нарисованную в Canvas пилюлю нажать нельзя — картинка не
кликается. Поверх кладётся `Button` **без фона и текста**
(`background="@android:color/transparent"`, `text=""`), она только ловит
нажатие. Если оставить у неё фон или подпись, поверх нарисованной пилюли
ляжет вторая, системная. Отступы кнопки-ловушки обязаны совпадать с
геометрией нарисованной пилюли до децибела — иначе палец попадает мимо.

**Один layout на два оформления — мина.** «Капля» и «кольца» делили
`fitflow_widget_p5`. Как только «кольцам» понадобились прозрачные кнопки,
«капля» осталась бы без видимых кнопок вообще. Решение: `layoutRes()` в
`FitFlowWidgetCanvasProvider` сделан переопределяемым, у «колец» своя
разметка. **Правило: меняете общую разметку — проверьте всех, кто её
использует** (`grep` по имени layout в `build.yml`).

**Подбор текста под место.** В Canvas нет `ellipsize` и `autoSizeText`,
их надо писать руками:

- *единый кегль списка* — подбирается по самой длинной строке в цикле
  `while (size > minSize)`, иначе строки будут разного размера;
- *подпись не режем* — «1 600 / 2 200 ккал» без слова «Питание» читается
  хуже; уменьшаем кегль, а не выбрасываем слова;
- *текст в круге* — считается от диаметра просвета, а не от размера
  виджета. Для даты сделан каскад вариантов: «28.08.2026 / пятница» →
  «28.08 / пт» → «28.08». Обрезать дату многоточием нельзя — получится
  «28.08.20…», что выглядит как ошибка.

**Проверка без телефона.** Для Canvas-виджета предпросмотр обязателен:
`python3 tools/widget-glass-preview.py`. Скрипт объявлен **зеркалом**
Java-кода, а тест сверяет ключевые числа (радиус кольца, шаг и толщины
дуг, шаг строк, высоту и отступ кнопок). Разъедутся — предпросмотр
начнёт врать, и вёрстку можно будет проверить только сборкой APK.

### 13.6. Что выяснилось на живом устройстве (0.9.33)

Виджет, безупречный в предпросмотре, на экране телефона показал шесть
недочётов. Выводы на будущее:

1. **Значки рисуйте эмодзи, а не геометрией.** Контур из линий и дуг в
   размере 11 dp превращается в кляксу. Эмодзи (`💧 🔥 👟`) рисуются обычным
   `drawText` шрифтом системы, они цветные и есть в любом Android — картинки
   в проект добавлять не нужно, настраиваемость виджета не страдает.
2. **Прозрачность не «прорезает» дырку.** Под виджетом обои пользователя:
   `PorterDuff.CLEAR` в стеклянной карточке пробьёт настоящую дыру. Просвет
   (например, в шестерёнке) делайте обводкой.
3. **Ловушка нажатия обязана скрываться вместе с рисунком.** Пилюлю рисует
   Canvas, а нажатие ловит прозрачная `Button`. Убрали кнопку из рисунка —
   спрячьте и ловушку через `View.GONE`, иначе палец попадёт в пустоту.
   Порядок кнопок в рисунке и в разметке должен совпадать.
4. **Число строк считайте от реальной высоты ячейки.** Владелец просил
   крупный шрифт, поэтому подстраивается количество строк, а не кегль:
   `maxRows = (высота полосы) / (шаг строки)`, лишнее тихо отбрасывается.
5. **Полоса списка начинается под элементами шапки.** Если считать от верха
   карточки, последняя строка залезет под шестерёнку и оборвётся.
6. **Состояние показывайте там, где действие.** Отметку о приёме витаминов
   вынесли на саму кнопку («1/2» / галочка), не тратя строку списка.

### 13.7. Второе оформление — темой, а не копией (0.9.34)

Понадобился светлый вариант «колец» под светлые обои. Соблазн — скопировать
`drawNeon()` и поменять цвета; так делать нельзя: любая правка компоновки
потом вносится дважды и рано или поздно расходится.

Как сделано:

1. Все цвета собраны в `NeonTheme` (заливка стекла, кромка, текст, приглушённый
   текст, шестерёнка, дорожка кольца, флаг свечения и четыре цвета дуг).
2. `drawNeon(..., NeonTheme th)` — единственная реализация. `drawNeon(...)`
   и `drawNeonLight(...)` только подставляют `NEON_DARK` / `NEON_LIGHT`.
3. **Разметка общая.** Прозрачные кнопки-ловушки не зависят от цвета, а
   второй одинаковый XML — мина (см. § 13.2 про общий layout).
4. У нового провайдера **свой `requestCodeBase`** (шаг не меньше 5, занято
   `base+1..base+4`), иначе кнопки одного виджета дёргают действия другого.
   Это стережёт тест.
5. Провайдер регистрируется в трёх местах: манифест, `*_info.xml` и
   `CANVAS_PROVIDERS`. Забыть последнее — виджет не обновится по кнопке воды
   и в полночь.

**Про цвет:** неоновое свечение на белом фоне выглядит грязным пятном,
поэтому в светлой теме размытые слои и светлая жила отключены флагом `glow`,
а цвета дуг взяты темнее — иначе они бледнят.

**Про значки:** значок показателя должен быть ОДИН и тот же в списке и на
кнопке — их рисует общая `neonIcon(id, ...)`. Эмодзи, у которых смысл
расходится с показателем, заменяются вектором: ⚖️ — «весы правосудия», для
веса тела нужен порт напольных весов из приложения.

### 13.8. Имя виджета, свои значки и анимация (0.9.35)

**Имя в системном списке.** Подпись, которую видит пользователь при выборе
виджета, берётся из `android:label` **на теге `<receiver>` в манифесте**.
В `appwidget-provider` xml тоже есть `android:label`, но лаунчер его для
списка не использует — без метки на ресивере все виджеты называются именем
приложения. Проверяется тестом.

**Свои PNG-значки.** Кладутся в `assets/widget-icons/<id>.png`, сборка
копирует их в APK, натив читает через `iconAsset()`. Порядок выбора:
свой PNG → векторный значок (весы) → эмодзи. Суффикс `-color` в имени
означает «не перекрашивать». Обязателен кэш в памяти процесса: без него
декодирование PNG на каждый кадр съедало бы анимацию. Отрицательный
результат («файла нет») тоже кэшируется.

**Анимация.** Виджеты не анимируются: RemoteViews умеет только заменить
картинку целиком. Плавность делается пачкой перерисовок —
`animateWater()` шлёт 12 кадров по 40 мс через `Handler`, с ease-out.
Правила:

1. **Только по событию** (нажатие). Постоянной анимации быть не должно —
   каждый кадр это `updateAppWidget`, то есть IPC и перерисовка лаунчера.
2. **Ограничьте число кадров константой** и стерегите её тестом.
3. Последний кадр рисуйте с `pct = -1` (по реальным данным), иначе при
   расхождении расчёта останется «подвисшее» промежуточное значение.

**Грабля:** общие помощники видимости (`showWaterOnly()`) трогают кнопки по
id, которых в новой разметке может не быть. Для виджета со своим набором
кнопок выставляйте видимость вручную.

## 14. Пустые слоты и нечисловые показатели

Два требования, которые бенто **не** решает. В «кольцах» (0.9.32) оба уже
реализованы — ниже и замысел, и то, как это сделано.

**1. Скрытый показатель не должен оставлять дыру.** У бенто плита
жёстко привязана к своей клетке подложки: спрятали слот C — на его месте
осталась пустая плита картинки. Это прямое следствие того, что геометрия
живёт в PNG. Решения два:

- *перетекающая раскладка*: подложка рисует только внешнюю оболочку (или
  её вообще нет — фон делает `drawable` со скруглением и полупрозрачной
  заливкой, «стекло»), а плиты рисует overlay `LinearLayout`'ами
  с `layout_weight`. Скрытый слот получает `View.GONE`, и веса
  перераспределяются сами — дыры не остаётся. Цена: тени и блики придётся
  делать средствами `drawable`, а не рисованным PNG;
- *набор готовых подложек* под 1/2/3 слота и выбор нужной в провайдере
  через `setImageViewResource`. Проще, но множит ассеты.

Для стекла взят первый путь: полупрозрачный фон всё равно нельзя
запечь в PNG — под ним обои пользователя.

**Как решено в «кольцах».** Дыр там не бывает by design: и дуги, и строки
рисуются циклом по списку выбранных показателей. Меньше показателей —
меньше колец и строк, а блок строк центрируется по кольцу, поэтому
раскладка остаётся плотной при любом составе. Порядок берётся из
`d.order()`: `HashSet` в `FitFlowWidgetData` его терял, пришлось завести
параллельный упорядоченный список.

**2. Показатель без числовой пары «значение / цель».** Пример — «Тренировка»:
у неё нет процента, есть состояние «сегодня тренировка» / «день отдыха».
В бенто такие показатели отсеиваются списком `SUPPORTED`, потому что плита
без шкалы выглядела бы сломанной. В новом виджете слот должен уметь два
режима:

```
режим «шкала»    подпись + значение + цель + ProgressBar
режим «статус»   подпись + короткая строка состояния, ProgressBar = GONE
```

Правило прежнее и важное: **никаких видимых заглушек**. Нет тренировки на
сегодня — пишем «отдых», а не «—» и не пустое место.

**Как решено в «кольцах».** Массив `NEON_RINGED` перечисляет показатели,
у которых есть числовая пара; кольцо рисуется только им. `workout` в
список не входит и получает строку со значком гантели — пустых дуг не
возникает. Саму строку считает `app.js` (`widgetWorkoutLine`) и кладёт в
prefs `workoutLine`; натив только отрезает префикс «Тренировка: »
(`d.workoutShort()`) и ничего не вычисляет — он не знает ни про шаблоны,
ни про план недели.
